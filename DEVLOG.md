## Package 002 – Bootstrap

Argus Factory reconciled two conflicting implementation packages (001_FOUNDATION and 002_BOOTSTRAP, which both targeted the same files with diverging scope). The Architect retired 001 as historical documentation and confirmed 002 as authoritative.

Built the foundational application framework: a dependency injection Container, a minimal Configuration loader, a Logging Service wrapping the standard library, and an Application lifecycle (start/shutdown), wired together by a single `bootstrap()` function. `python main.py` now runs this sequence instead of launching the legacy Shell.

Two things came up worth carrying forward:

Order of initialization matters. LOGGING.md states Logging depends on Configuration, so Configuration loads first and Logging initializes from it — not the other way around.

Configuration Service's own specification lists Event Bus as a required dependency, but Event Bus is out of scope for this package. Resolved by scoping this package's Configuration to a one-time startup load with no change notification; wiring to the Event Bus is deferred until that package exists.

The interactive Shell still exists in the codebase but is no longer started from `main.py`. It predates the Factory architecture and needs to be reintroduced deliberately as an application on top of this foundation, not bypassed around it.

The coding standard was also consolidated: `CODING_STANDARDS.md` and `coding.md` were merged into a single canonical `factory/standards/CODING_STANDARD.md`.

## Package 002 – Bootstrap (architecture review correction)

Architecture review caught a real gap: the test suite booted fine in isolation but `python -m unittest` and `python -m unittest discover` found zero tests, and `pytest` wasn't installed in the review environment. Verified `python -m unittest`, `python -m unittest discover`, and `python -m unittest discover -s tests` all find and pass the full 21-test suite with no dependencies beyond the standard library, consistent with the coding standard's preference for the standard library over new dependencies.

## Package 003 – Event Bus

Built the publish/subscribe communication backbone: an immutable `Event` (frozen dataclass, UUID + UTC timestamp auto-generated, payload/metadata wrapped in `MappingProxyType` so no handler can mutate what it receives), an `IEventBus` contract, and `InMemoryEventBus` — a synchronous, in-process implementation with explicit validation for null events, invalid types, missing sources, non-callable handlers, and duplicate subscriptions.

A few judgment calls, all grounded directly in the spec text rather than invented:

`publish()` validates the event, times the dispatch, and logs type/source/priority/handler-count/duration; `dispatch()` is the separate, unvalidated handler-invocation primitive the interface also requires. Splitting them this way is the only reading that doesn't make one of the two interface methods redundant.

`EventPriority` defaults to `NORMAL` — implied by the acceptance scenario, which constructs an `Event` without a priority.

Registered `InMemoryEventBus` in the Container from `bootstrap.py` only. Left `Application.start()`/`shutdown()` untouched — the work order's objectives call for DI registration, not for lifecycle wiring, and Package 002's lifecycle was explicitly marked "preserve exactly." Flagged as a natural next package rather than folded in here.

All 21 Package 002 tests plus 27 new tests pass under `python -m unittest discover` — 48 total, no pytest anywhere.

## Package 004 – Service Registry

Built the operating system's authoritative service directory: an immutable `ServiceDescriptor` (name/instance/interface/version/state/metadata, metadata wrapped in `MappingProxyType` the same way `Event`'s payload/metadata were in Package 003), a `ServiceState` enum, an `IServiceRegistry` contract, and `InMemoryServiceRegistry` — a deterministic, name-keyed registry with explicit exceptions for duplicate registration and unknown-name lookups.

A few decisions worth flagging:

`register()` takes a fully-constructed `ServiceDescriptor` rather than loose parameters — keeps the "no business logic" constraint on `ServiceDescriptor` honest (it's pure data; the registry doesn't build it) and keeps `InMemoryServiceRegistry` focused purely on storage/lookup.

`resolve()` returns the raw service instance (`descriptor.instance`), not the descriptor, matching `Container.resolve()`'s existing behavior; `list_services()` returns the full descriptors so callers can still introspect version/state/metadata/interface when enumerating.

`unregister()` of a name that was never registered raises `ServiceNotFoundError` rather than no-op — same reasoning as `EventBus.unsubscribe()` in Package 003: "never silently fail" plus the established precedent.

`ServiceState` has no separate module: the work order's package structure lists five files with no room for a `service_state.py`, so it lives in `service_descriptor.py` next to the dataclass that uses it, the same way `EventType`/`EventPriority` both live in `event_types.py`.

Registered `InMemoryServiceRegistry` in the Container from `bootstrap.py` only, in the exact position specified (between Event Bus and Application). Did not populate the registry with the existing services (Configuration, Logger, Event Bus) — the spec's Bootstrap Integration section asks for registering the Service Registry itself, not for using it yet.

## Package 005 – Service Lifecycle

Built the common lifecycle contract and state machine every ArgusOS service will eventually implement: `IService` (initialize/start/stop/status), `LifecycleState` (seven states), and `LifecycleManager`, an in-memory, per-name state machine with an explicit legal-transition graph.

The one real gap in the spec: the "Suggested public API" lists five methods (register/initialize/start/stop/status), but the transition rules require a `FAILED` state reachable from "any active state," and none of those five methods can produce it — `initialize`/`start`/`stop` each move forward exactly one step in the happy path, and `status` is read-only. Added a sixth method, `fail(service_name)`, since there's no other way to satisfy an explicit requirement in the same document. Documented prominently rather than silently added, since it's the most consequential judgment call in this package.

The other structural note: `stop()` has to cover two edges (`RUNNING`→`STOPPING`→`STOPPED`) in one call, since there's no separate method for the second edge. It's implemented as one validated transition into `STOPPING` immediately followed by a direct write to `STOPPED` — no timers, no background step, matching "no timers, no background workers."

Registered the five core services (Configuration, Logger, Event Bus, Service Registry, Lifecycle Manager) into both the Service Registry (finally closing the gap Package 004 flagged as a known limitation) and the Lifecycle Manager, all landing on `REGISTERED` and nothing further, exactly as instructed. Used `"0.0.5"` as the version on their `ServiceDescriptor`s, taken from this work order's own version target header.

Flagged one open architecture question rather than resolving it myself: `ServiceDescriptor.state` (Package 004) and `LifecycleManager`'s `LifecycleState` (Package 005) are now two parallel, unsynchronized "state" concepts tracking the same five names. Not this package's job to unify them, but worth the Architect's attention before more services start relying on either one.

99 tests total (72 from Packages 002-004 plus 27 new), all passing under `python -m unittest discover`, no pytest anywhere.

## Package 005 – Architectural Revision (duplicate state elimination)

Architecture review caught exactly the thing flagged as a known limitation when Package 005 first shipped: `ServiceDescriptor.state` and the Lifecycle Manager's `LifecycleState` were two independent models of the same concept, set together but never kept in sync. Asked to make the Lifecycle Manager the sole owner and eliminate the duplicate before acceptance.

Removed `state` from `ServiceDescriptor` and deleted `ServiceState` outright — searched the whole tree for it first to make sure nothing else depended on it (nothing did; only `service_descriptor.py`, `services/__init__.py`, and `bootstrap.py`'s construction call ever touched it). `ServiceDescriptor` is now pure identity/descriptive data: name, instance, interface, version, metadata. Runtime state lives in exactly one place now.

This breaks `ServiceDescriptor`'s constructor signature. Didn't try to preserve backward compatibility with a stray optional `state` parameter that goes nowhere — the revision request was explicit that eliminating the duplicate takes priority, and the only callers were `bootstrap.py` and the test suite, both already fixed.

Verified end to end: `python main.py` clean, all 99 tests passing, and a manual bootstrap check confirming no core service's `ServiceDescriptor` carries a `state` attribute while every core service still correctly reports `LifecycleState.REGISTERED` from the Lifecycle Manager.

## Package 006 – Knowledge Service

Built ArgusOS's first persistent knowledge subsystem: `KnowledgeRecord` (immutable, category + globally-unique key + value + timestamps + version), `IKnowledgeStorage`/`JSONKnowledgeStorage` (one JSON array file per category, every write atomic via temp-file + `os.replace`), and `KnowledgeService` (the CRUD orchestrator, eager in-memory key index, write-locked, event-publishing).

The one real design decision the work order left open: how to satisfy "Publish events on the existing Event Bus. Examples: KnowledgeCreated, KnowledgeUpdated, KnowledgeDeleted" given `InMemoryEventBus._validate_event` strictly requires `isinstance(event.type, EventType)`. Extended `EventType` with `KNOWLEDGE_CREATED`/`KNOWLEDGE_UPDATED`/`KNOWLEDGE_DELETED` rather than inventing a side channel — `event_types.py`'s own docstring says outright that this module is "the single place new event types are added," and a repo-wide search turned up no test that asserts `EventType`'s membership is closed. Naming follows the exact convention already in use (`SYSTEM_STARTED`, `SERVICE_STARTED`, ...).

Kept the in-memory index as a single flat `Dict[key, KnowledgeRecord]` rather than nesting it by category, since keys are specified as globally unique — a flat map is the simplest structure that satisfies that constraint, at the cost of `_persist_category` doing an O(n) scan over the whole index on every write to rebuild just one category's file. Documented as a known limitation rather than over-engineered away, per the package's "intentionally simple" v1 scope.

Published events after releasing the write lock, not while holding it. `threading.Lock` isn't reentrant, and a future subscriber calling back into `KnowledgeService` (e.g. `get()`, or another `put()`) from inside a handler would deadlock if the lock were still held during dispatch. Reads (`get`/`exists`/`list`) stay unlocked throughout, exactly as the work order specifies ("Reads may remain unlocked for v1").

Registered `KnowledgeService` as ArgusOS's sixth core service, immediately after the Lifecycle Manager and before the core-service registration loop, since it depends on the Event Bus (already constructed) and needs to exist before anything can query it. Like the other five, it's registered in both the Service Registry and the Lifecycle Manager (`LifecycleState.REGISTERED`) but never initialized or started — `KnowledgeService` doesn't implement `IService` in this package, matching the treatment of Configuration, the Logger, the Event Bus, the Service Registry, and the Lifecycle Manager itself to date. Bumped `CORE_SERVICES_VERSION` to `"0.0.6"`, this work order's version target.

One process note worth flagging: the work order's Founder Verification Checklist says "Only expected new files should appear" in `git status`, but the Registration requirement explicitly calls for wiring `KnowledgeService` into `bootstrap.py` as a core service — that can only be done by modifying the existing `argus/bootstrap.py`, and satisfying the Events requirement can only be done by modifying the existing `argus/events/event_types.py` (plus `tests/test_bootstrap.py`, to keep its six-core-service assertions accurate). Treated the Registration and Events sections as the more deliberate, specific instructions and proceeded with those three modifications, since leaving `KnowledgeService` unregistered or unable to publish events to satisfy a terser checklist line seemed like the wrong tradeoff — flagging it here rather than resolving it unilaterally.

140 tests total (99 from Packages 002-005 plus 41 new: 8 for `KnowledgeRecord`, 12 for `JSONKnowledgeStorage`, 20 for `KnowledgeService` (including two covering empty-key/empty-category validation), and 1 extending `test_bootstrap.py`), all passing under `python -m unittest discover`, no pytest anywhere. Coverage on every new module is 100% except `storage.py` at 91% (two untested OS-failure branches in the atomic-write path).

## Package 007 – Memory Service

First package where I was asked to pick the target, not just implement a handed-down work order. Before writing anything, audited every unimplemented engine in `design/specifications/` (Atlas, Cortex, Hermes, Navigator, Scheduler, Sentinel, Memory) against their own stated Required Dependencies. Only two have every dependency already satisfied by what's actually built: Memory (Logging, Configuration, Event Bus) and Sentinel (Event Bus, Logging, Configuration). Everything else is blocked — Scheduler needs Navigator, Hermes needs Cortex, Navigator needs Cortex+Hermes+Scheduler, Atlas needs Memory, and Cortex has no specification file in the repository at all, so building it would mean inventing architecture rather than implementing it.

Between the two unblocked options, picked Memory over Sentinel because Memory sits on the critical path — Atlas's spec explicitly lists Memory Service as a Required Dependency, so building Memory is the next concrete step toward every reasoning-capable engine. Sentinel has nothing to govern yet: no engine that executes autonomous actions (Navigator, Hermes) exists, so a security/governance layer would be built ahead of anything it protects. Also noticed `EventType.MEMORY_UPDATED` has sat reserved and unused in `event_types.py` since Package 003 — the same kind of signal that correctly anticipated `KNOWLEDGE_*` before Package 006. Wrote the full audit into `factory/packages/007_MEMORY_SERVICE.md` so the reasoning is part of the repository, not just this log entry.

The one real design question: how does Memory Service differ from Package 006's Knowledge Service, given both are JSON-backed, versioned, event-publishing CRUD stores? Landed on expiry as the defining, non-overlapping feature. `MemoryRecord` carries an `expires_at` that `KnowledgeRecord` doesn't; Memory Service is for short-term, working-context data (the kind Atlas/Cortex will eventually read and discard), while Knowledge Service stays scoped to durable, human-curated facts with no concept of expiry at all. Implemented expiry lazily rather than with a background sweep thread: `get`/`exists`/`list`/`search` all treat an expired record as absent without touching storage, and only the new `purge_expired()` method physically removes anything, taking the write lock like every other mutation. This keeps Memory Service consistent with "no timers, no background workers" — a principle that's now shown up in the Event Bus's, the Lifecycle Manager's, and now Memory Service's Non-Goals — and sidesteps having to reason about a thread's lifecycle at all.

Considered making `MemoryService` implement `IService` — its natural `start()` would be a good place for a background expiry sweep, which the `MEMORY.md` spec's "Retention Manager" component gestures at. Decided against it. Every `IService` implementer has to track its own internal `LifecycleState` (the interface's `status()` method demands it), which sits alongside whatever the Lifecycle Manager tracks by name for that same service — structurally the same two-sources-of-truth shape that the Package 005 revision spent real effort eliminating for `ServiceDescriptor`. Adopting `IService` for the first time is a genuine architectural decision, not a detail to fold into a data-service package's scope. Left it explicitly out of scope, `MemoryService` registers with the Lifecycle Manager as `REGISTERED` only, exactly like all six other core services to date.

Reused `EventType.MEMORY_UPDATED` as-is rather than adding `MEMORY_CREATED`/`MEMORY_DELETED` the way Package 006 added three new `KNOWLEDGE_*` members. `MEMORY_UPDATED` was clearly reserved for exactly this purpose, and a single event type with an `operation` field in the payload (`created`/`updated`/`deleted`/`purged`) covers every mutation without touching `event_types.py` at all — a smaller footprint than Package 006's approach, and a deliberate response to the "only expected new files should appear" tension flagged in that package's report.

Registered Memory Service as ArgusOS's seventh core service, immediately after the Knowledge Service, since it depends only on the Event Bus (already constructed). `CORE_SERVICES_VERSION` bumped to `"0.0.7"`.

196 tests total (140 from Packages 002-006 plus 56 new: 13 for `MemoryRecord`, 12 for `JSONMemoryStorage`, 30 for `MemoryService`, and 1 extending `test_bootstrap.py`), all passing under `python -m unittest discover`, no pytest anywhere. Coverage on every new module is 100% except `storage.py` at 90% (two untested OS-failure branches in the atomic-write path, same shape as Package 006's).

## Package 008 – Scheduler Service

Built ArgusOS's time orchestration layer: `ScheduledTask` (immutable, priority-ordered), three `Trigger` implementations (`OneShotTrigger`, `IntervalTrigger`, `DailyTrigger`, all using a uniform strict-`>` `next_fire_time(after)` contract so no trigger ever refires on the tick immediately after it fires), and `Scheduler`, which executes due tasks only when `tick()` is called — no background thread, no timer, fully deterministic under an explicit `now`.

Hit a real bug early: `schedule()` originally called `datetime.now(timezone.utc)` internally with no override, the same way every prior package's mutation methods do. But Scheduler is different — its own tests need to control *two* points in time (when a task is scheduled, and when it's ticked), not just one. Discovered this the hard way: a batch of tests scheduling `OneShotTrigger(run_at=NOW)` and ticking later all failed, because the sandbox's real clock is mid-2026 while the test fixture's `NOW` constant is January 2026 — `schedule()` was computing `next_run` against the wrong "now" entirely. Fixed by adding an optional `now` parameter to both `schedule()` and `resume()`, mirroring `tick()`'s existing pattern. Once fixed, a second, more interesting bug surfaced: several tests scheduled a `OneShotTrigger` for exactly the same instant as the schedule-time `now`, which correctly returns `None` under strict-`>` semantics (a one-shot due "now" is treated as already elapsed, not still pending) — so the tests themselves were wrong, not the trigger logic. Fixed by scheduling one second after the reference time throughout, which is also a more realistic pattern than "due literally the instant it's created."

`IScheduler` inherits `IService`, as instructed — and as `IService`'s own Package 005 docstring anticipated four packages ago. Gave `start()`/`stop()` real, non-decorative meaning despite the "no background thread" constraint: `tick()` raises `SchedulerError` unless the Scheduler's own state is `RUNNING`, so start/stop genuinely gate execution rather than being bookkeeping for its own sake. Registry operations (`schedule`/`cancel`/`pause`/`resume`/`get_task`/`list_tasks`) are deliberately unaffected by lifecycle state — you can queue up work before the scheduler is started, which matches how real schedulers behave.

Per the Founder's explicit standing instruction from the ADR-0002 discussion — leave `IService` unchanged, use Scheduler as the proving ground, revisit only if the concern is confirmed — implemented Scheduler's `status()` exactly as the interface demands: a self-tracked internal `LifecycleState`, with no connection to whatever a `LifecycleManager` tracks for the same registered name. Then wrote a dedicated test (`IServiceLifecycleDivergenceTests`) that registers a `Scheduler` with a real `LifecycleManager` the way `bootstrap.py` does, calls `scheduler.initialize()`/`start()` directly without telling the `LifecycleManager`, and asserts the two now disagree. They do: `LifecycleManager` still reports `REGISTERED` while the object itself reports `RUNNING`. This is exactly the failure mode ADR-0002 predicted, now demonstrated with a passing, permanent regression test rather than just an argument. `bootstrap.py` itself avoids the problem by construction — it registers Scheduler with the `LifecycleManager` but never calls `scheduler.initialize()`/`start()` — but that's a discipline the framework doesn't enforce; nothing stops a future caller from doing what the test does.

Extended `EventType` with seven new `TASK_*` members for the seven required events, and finally put the long-reserved `SCHEDULER_TICK` (sitting unused since Package 003, the same vintage as `MEMORY_UPDATED`) to work as a per-`tick()` heartbeat, separate from the per-task events. Deliberately did not wire Scheduler's own `initialize()`/`start()` into `bootstrap.py`: nothing in this package ever calls `tick()` automatically, so starting it during bootstrap would have no behavioral effect beyond flipping an internal flag, while also being the first bootstrap-time exercise of the exact `IService`/`LifecycleManager` pairing this ADR is watching for trouble in. Kept bootstrap registration uniform with all seven prior core services (`REGISTERED` only) and proved the `IService` contract works correctly through direct unit tests instead.

281 tests total (196 from Packages 002-007 plus 85 new: 18 for triggers, 10 for `ScheduledTask`/`TaskPriority`, 56 for `Scheduler` (including the divergence test and a test added during coverage cleanup for a task that cancels itself mid-execution), and 1 extending `test_bootstrap.py`), all passing under `python -m unittest discover`, no pytest anywhere. Coverage is 100% on every new module except the abstract `Trigger.next_fire_time` stub (98% on `triggers.py`, same shape as every other ABC in this codebase — the stub body is never reachable since every concrete trigger overrides it).

## Package 009 – Intent Router

Built ArgusOS's first text-classification layer, with a hard constraint running through the whole design: deterministic, rule-based parsing only — no AI, no ML, no external libraries, no regex-heavy heuristics. `parser.py`'s `parse_text()` is a pure function over fixed keyword tuples and a fixed precedence order (question mark/word, then command verb, then memory keyword, then schedule keyword, then unknown), using a simple `_starts_with_word` word-boundary check (`normalized == word or normalized.startswith(word + " ")`) rather than anything regex-based. Verified all four of the work order's given examples classify correctly via a direct smoke test before writing a single formal test.

The real design tension in this package was reconciling two requirements that read as being in conflict: `register_handler(intent_name, handler)` must exist as a first-class method, and routing must go through "Intent → Event Bus → Interested services respond" with no direct service invocation. Resolved it by making `register_handler` pure sugar over the Event Bus: it builds a small adapter closure that subscribes to `EventType.INTENT_ROUTED`, filters by `event.payload["name"] == intent_name.value`, reconstructs an `Intent` from the payload, and calls the handler — catching any exception the handler raises and publishing `IntentFailed` instead of letting it propagate, mirroring Scheduler's per-task failure isolation from Package 008. This means `route()` has exactly one invocation mechanism, a single `self._event_bus.publish(...)` call — nothing in `IntentRouter` ever calls a registered handler directly. Proved this structurally, not just by convention: one test (`test_route_only_invokes_handlers_via_the_event_bus_publish_call`) registers a handler *after* `route()` has already published and confirms it never fires, and another (`test_handler_is_not_invoked_directly_by_route_without_event_bus`) registers a handler on a second `IntentRouter` sharing no Event Bus with the first and confirms it's never called — if `route()` had any hidden direct-dispatch path, either test would catch it.

`IIntentRouter` inherits `IService`, per the work order, and `IntentRouter` tracks its own `LifecycleState` the same way `Scheduler` does — `CREATED → INITIALIZING → RUNNING → STOPPED`, raising `IntentError` on illegal transitions. But unlike `Scheduler`, there is nothing here for `start()`/`stop()` to genuinely gate: `parse()`, `route()`, and `register_handler()` all behave identically no matter what lifecycle state the router is in. Rather than paper over this, wrote it into the module docstring explicitly and added a dedicated test (`test_parse_route_and_register_handler_are_not_gated_by_lifecycle_state`) asserting the current, honest behavior — so if a future package adds real gating, that test forces the change to be a deliberate, visible decision rather than an accidental regression. This is a meaningfully different shape than Scheduler's `IService` adoption: Scheduler proved the ADR-0002 duplicate-state risk is real *and* that `IService` can carry genuine behavior; IntentRouter shows `IService` can also be adopted with zero behavioral gate, purely to satisfy an interface contract. Appended this as a second data point to ADR-0002 rather than opening a new ADR — it's additional evidence for the same open question, not a distinct decision.

Extended `EventType` with three new members: `INTENT_PARSED` (fires on every `parse()` call, including `UNKNOWN` results — the router never treats "no match" as a failure), `INTENT_ROUTED` (fires on every successful `route()` call, and is what `register_handler()`'s adapters filter from), and `INTENT_FAILED` (fires for router-level input failures — non-string `parse()` input, non-`Intent` `route()` input — and, separately, for isolated per-handler failures during `register_handler()`'s dispatch). Registered `IntentRouter` as ArgusOS's ninth core service, immediately after Scheduler, following the exact same `REGISTERED`-only bootstrap treatment already established for all eight prior core services — including Scheduler, despite it being the second consecutive package to genuinely implement `IService`.

Caught one design bug of my own while writing the parser test suite: a memory-keyword test used `"note: buy milk"`, expecting `subject="buy milk"` to be extracted. It wasn't — `_starts_with_word` requires the keyword to be followed by a space or end-of-string, so `"note:"` (colon immediately after, no space) doesn't match the leading-keyword check at all and falls through to the weak-confidence substring path instead, with no subject extracted. This is a real, if narrow, limitation of the simple rule-based matcher (no punctuation normalization) — not a bug worth fixing under the "simple rule-based parsing only" constraint, so it's documented as a Known Limitation and the test now asserts the actual, correct-per-spec behavior instead of the behavior I'd initially assumed.

This package was regenerated once. The first attempt was built against a reconstructed workspace whose Package 008 baseline (281 tests) turned out not to match the Founder's live repository's reported count (369). Investigation of the Founder's actual repository (supplied as a zip export) found the discrepancy had nothing to do with any tests being removed: the live repo carries a stray, stale duplicate of parts of itself nested inside `argus/` (`argus/tests/`, `argus/lifecycle/test_lifecycle.py`, `argus/CHANGELOG.md`, `argus/DEVLOG.md`, `argus/factory/`), left over from an earlier merge, plus a `.pytest_cache/` whose cached node-id list — 369 entries — proved the exact arithmetic: 281 canonical + 24 duplicated from `argus/lifecycle/test_lifecycle.py` + 64 duplicated from `argus/tests/*`. Every canonical file this package actually touches (`argus/bootstrap.py`, `argus/events/event_types.py`, `tests/test_bootstrap.py`, `CHANGELOG.md`, `DEVLOG.md`, `factory/ROADMAP.md`, ADR-0002) was verified byte-identical to the reconstructed workspace's version by direct diff before regenerating, so the actual Package 009 implementation carried over unchanged. Per the Founder's explicit instruction, the stray duplicate and legacy pre-Factory files (`argus/brain.py`, `argus/conversation.py`, etc.) were left untouched as out of scope, reserved for a dedicated future cleanup package.

## Package 010 – Workflow Engine

Built ArgusOS's first multi-step orchestration layer. The central design tension, stated almost verbatim in the work order, was "coordinates multiple Argus services" versus "the engine must never directly invoke unrelated services outside its defined interfaces." Resolved it the same way Package 009 resolved the Intent Router's analogous tension: `WorkflowEngine` never imports or references `argus.knowledge`, `argus.memory`, `argus.scheduler`, or `argus.intent` anywhere (verified by a test that inspects `engine.py`'s own source for those import strings). A `WorkflowStep`'s `action` is an opaque callable — `Callable[[Mapping], Mapping]` — that the engine invokes without any idea what it does. Coordinating "multiple Argus services" happens *inside* a step's action, constructed by whoever builds the `WorkflowStep` (resolving whatever service it needs from the Container) — never inside the engine itself. This keeps `WorkflowEngine` exactly as decoupled as `IntentRouter`, just via plain callables instead of Event Bus subscriptions, since a workflow step is a synchronous unit of work rather than a fire-and-forget reaction to an event.

`Workflow` is a frozen dataclass, same shape as `ScheduledTask` and `Intent` before it: `steps` gets wrapped in a tuple and `metadata` in `MappingProxyType` in `__post_init__`, so `WorkflowEngine` never mutates a `Workflow` in place — every state transition (`register_workflow`'s initial `PENDING`, `execute()`'s `RUNNING`→`COMPLETED`/`FAILED`, `cancel()`'s `CANCELLED`) goes through `dataclasses.replace()` and a fresh dict entry, exactly like `Scheduler`'s task registry.

`execute()` threads context sequentially: each step's action receives the accumulated context dict and returns the next one, which becomes the input to the following step. A step's exception is caught, wrapped in `WorkflowExecutionError` (constructed but never raised past `execute()` — it exists for symmetry with `TaskExecutionError` and to give the caught error a documented type), and turned into a `WorkflowFailed` event plus a `FAILED` state transition; remaining steps never run. This is a direct copy of Scheduler's per-task failure isolation philosophy from Package 008, applied to *steps within one workflow* instead of *tasks within one tick()*.

The one real architectural decision this package makes on its own initiative: `IWorkflowEngine` needed a `get_workflow()` lookup method beyond the four literally-named "Required Methods" (`register_workflow`/`execute`/`cancel`/`status`), because the work order's own testing requirements list "Status reporting" as an expected coverage area, and `IService.status()` only reports the *engine's* lifecycle state — there is no way to ask "what state is workflow X in?" without a per-workflow lookup. Added `get_workflow(workflow_id) -> Workflow`, documented explicitly as an addition (not a silent scope expansion) in both `interfaces.py`'s docstring and `IMPLEMENTATION_REPORT.md`'s Deviations section — the same treatment given to Scheduler's added `now` parameter in Package 008 and to `get_task()`/`list_tasks()` themselves, which the Scheduler work order *did* name explicitly (Workflow's did not, making this package's addition slightly more of a judgment call, flagged accordingly).

The second real decision: whether `execute()` should be gated on the engine's own `IService` lifecycle state, the way `Scheduler.tick()` is, or left ungated, the way `IntentRouter`'s methods are. Went with genuine gating. `IService`'s own docstring frames `start()`/`stop()` as bracketing "the service's active work," and running a workflow's steps is unambiguously that — a much closer match to Scheduler's `tick()` than to IntentRouter's stateless `parse()`/`route()`. `register_workflow()`, `cancel()`, and `get_workflow()` stay ungated, mirroring Scheduler's registry operations being unaffected by lifecycle state. This makes WorkflowEngine the second of three `IService` adopters (after Scheduler, unlike IntentRouter) where the interface does genuine work, and I appended that finding to ADR-0002 as reinforcing evidence rather than a new complication — three data points now, two showing a real gate, one showing none, all consistent with the original proposed criterion ("adopt `IService` only when `start()`/`stop()` would do real, distinct work").

## Package 011 – Conversation Manager

Built ArgusOS's first cross-service coordinator: `ConversationManager` maintains a session's state and message history and, for each incoming message, delegates classification to `IntentRouter` and (optionally) execution to `WorkflowEngine` — never doing either itself. The mission statement's own wording drew the boundary precisely: "delegates intent parsing," "delegates execution," "never performs AI reasoning," "never parses intents itself," "never executes workflows itself." Enforced this the same structural way Packages 009 and 010 enforced their own analogous boundaries: `manager.py` never imports `argus.intent.parser` (the actual classification logic) or `argus.knowledge`/`argus.memory`/`argus.scheduler`, verified by a test that inspects the module's own source for those strings, not just documented as intent.

The one real design question the work order left open: what does "delegates execution to the Workflow Engine" mean concretely, given no workflow catalog or intent-to-workflow routing table was specified? Rather than invent one (which would have meant writing exactly the kind of business logic the work order says this manager must never contain), `receive()` accepts an optional, caller-supplied `workflow_id`. If given and currently registered in the Workflow Engine, `receive()` calls `IWorkflowEngine.execute()` and publishes `WorkflowExecuted`; if omitted, or if the workflow_id doesn't resolve (`WorkflowNotFoundError`) or can't run right now (`WorkflowError`, e.g. the engine isn't started), the call is skipped gracefully and `receive()` still returns a response — a failed or absent delegation never crashes a conversation turn. This keeps the coordination structurally real (a genuine `IWorkflowEngine.execute()` call happens, end to end, when asked) without ConversationManager inventing which workflow an intent "should" trigger.

Response generation is a small, fixed dictionary of templates keyed on `intent.name.value` (`"question"` → one string, `"command"` → another, and so on, with a default fallback) — explicitly not natural-language generation, consistent with "never performs AI reasoning." This mirrors `parser.py`'s own fixed-keyword-table design from Package 009: both modules turn a discrete classification into a discrete, table-driven output, no inference involved.

`IConversationManager` inherits `IService`, and `receive()` follows the now three-times-established pattern from Scheduler (`tick()`) and WorkflowEngine (`execute()`): gated on the manager's own state being `RUNNING`, while `start_session`/`end_session`/`history`/`active_session` stay ungated as registry operations. This makes ConversationManager the fourth `IService` adopter and the third with a genuine gate (only IntentRouter has none), a finding appended to ADR-0002 as further reinforcement of the original proposed criterion rather than a complication.

`ConversationState` gained a state, `ACTIVE`, that is never externally observable between two separate calls — `receive()` transitions `NEW`/`WAITING` → `ACTIVE` at its start and → `WAITING` at its end, entirely within one synchronous call, the same pattern `Workflow.state` used for `RUNNING` in Package 010 (a workflow's `RUNNING` state is likewise only ever visible to code running *during* `execute()`, e.g. a step inspecting its own workflow). Caught one genuinely dead branch while chasing 100% coverage on `manager.py`: a defensive `if session.state == ConversationState.CLOSED: raise ...` inside `receive()`, guarding against receiving on a closed active session. Traced through the state machine and found it provably unreachable — `end_session()` is the *only* code path that ever sets `CLOSED`, and it always clears `_active_session_id` in the same call, so `_require_active_session()` already raises `NoActiveSessionError` before a `CLOSED` session could ever be reached that way. Removed the branch rather than leave untested dead code, and updated `interfaces.py`'s docstring to explain the invariant instead of documenting behavior that could never occur.

Extended `EventType` with six new members bracketing a session's lifetime and each `receive()` call: `ConversationStarted`/`ConversationEnded` for the session, and `MessageReceived`/`IntentResolved`/`WorkflowExecuted` (conditional)/`ResponseGenerated` for one turn. ## Package 012 - Intent Dispatcher

Built the layer that sits between classification (IntentRouter, Package 009) and execution (WorkflowEngine, Package 010): `IntentDispatcher` translates a resolved `Intent` into an executable `Action` via a configurable mapping table, and delegates to that Action - never parsing an intent, never running a workflow's steps, never reasoning about anything itself.

The one real design question the work order raised explicitly - "should permit future Action implementations... without redesigning the dispatcher" - shaped everything else. The naive approach would have given `IntentDispatcher.__init__` an `IWorkflowEngine` parameter, matching `ConversationManager`'s own precedent (Package 011) of taking its two delegate services directly. Rejected that in favor of a cleaner cut: `Action` is a one-method abstract base class (`execute()`), and each concrete Action is constructed with whatever backend *it* needs - `WorkflowAction` takes a `workflow_id` and an `IWorkflowEngine`; a future `PluginAction` would take a plugin runner; an `AgentAction` would take an agent client. `dispatcher.py` itself ends up with zero references to `IWorkflowEngine` at all - confirmed by a source-inspection test, the same technique Packages 010 and 011 used to structurally prove their own loose-coupling claims. This isn't just cleaner - it's the literal difference between "the work order's extensibility requirement is true" and "the work order's extensibility requirement is aspirational."

Where do the dependencies actually get wired, then? `bootstrap.py`, and only `bootstrap.py`. It constructs the five `WorkflowAction` instances (one per `argus.dispatcher.mapping.DEFAULT_WORKFLOW_IDS` entry) and registers them into the dispatcher via `register_mapping()` - the only place in this package where a `WorkflowAction` is actually built. This mirrors the DI pattern established since Package 002: nothing except `bootstrap.py` constructs a concrete service or, now, a concrete Action directly.

The second open question: what do the five "Initial mappings" (QUESTION -> Answer Workflow, etc.) actually point to, given no other package has ever created a real "answer" or "command" workflow with real business logic? Followed the exact precedent `ConversationManager.receive()` already set for its own `workflow_id` parameter (Package 011): register the mapping as data (a `workflow_id` string, defined in `mapping.py`), and let `IWorkflowEngine.execute()`'s own `WorkflowNotFoundError` be the real, honest answer when nothing is registered under that id yet. `dispatch()` catches it, wraps it as `ActionExecutionError`, and publishes `DispatchFailed` with `stage="execute"` - a fully tested, by-design failure mode (see `tests/test_intent_dispatcher.py::DispatchFailureTests::test_dispatch_with_invalid_mapping_workflow_id_raises_action_execution_error`), not a bug to paper over by inventing five workflows' worth of unspecified business logic.

The six new events needed one extra hour of thought before implementation: the work order lists `IntentDispatched, ActionResolved, WorkflowSelected, DispatchStarted, DispatchCompleted, DispatchFailed` in that exact order, and reading it as the chronological publish sequence (the same way Package 011's six-event list read as chronological) resolves what would otherwise look like two redundant "started" events. `IntentDispatched` marks "this Intent has entered the pipeline" (right after validation, mirroring `MessageReceived` being first in Package 011's own list); `DispatchStarted` marks the later, narrower moment right before the resolved Action's `execute()` is actually invoked. `WorkflowSelected` sits between `ActionResolved` and `DispatchStarted`, and is the one genuinely Action-kind-specific event in the whole list - it only fires when the resolved Action happens to be a `WorkflowAction`, via a single `isinstance()` check inside `dispatch()` that reads `WorkflowAction`'s own `workflow_id` property. This is the one place `dispatcher.py` knows anything about a specific Action subclass, and it's deliberately narrow: nothing about *executing* the Action goes through that isinstance check, only the decision of which extra event to publish.

`IIntentDispatcher` inherits `IService`, and `dispatch()` follows the now four-times-established pattern from Scheduler, WorkflowEngine, and ConversationManager: gated on the dispatcher's own state being `RUNNING`, while `register_mapping`/`remove_mapping`/`resolve`/`list_mappings` stay ungated as registry operations. This makes IntentDispatcher the fifth `IService` adopter and the fourth with a genuine gate (only IntentRouter has none), appended to ADR-0002 as further reinforcement - now a 4-to-1 pattern across five independently-specified packages.

## Package 013 - Capability Registry

Built the layer the target architecture diagram inserted between Intent and Intent Dispatcher: `CapabilityRegistry`, a pure metadata store describing everything ArgusOS knows how to do, and a refactor of `IntentDispatcher` (Package 012) to query it live instead of holding its own `IntentType -> Action` mapping.

The central design tension, flagged in the work order itself ("If the current abstract Action class naturally becomes awkward... you MAY rename it... ONLY if it meaningfully improves the architecture"): does inserting a Capability layer force `IntentDispatcher` to start depending on `IWorkflowEngine` directly, undoing Package 012's whole point? Resolved it the same way Package 012 resolved its own analogous tension: `Capability` stays pure data (no live service reference, matching every other value object in this codebase), and a new function, `build_action_from_capability()`, is the one place a Capability's `action_kind` gets interpreted into a constructed `Action`. `IntentDispatcher` never calls this function directly - it receives it pre-built as an injected `action_factory` callable, the same opaque-callable idiom `StepAction` (Package 010) and `ScheduledTask.callback` (Package 008) already established. `bootstrap.py` is the only place `functools.partial(build_action_from_capability, workflow_engine=workflow_engine)` happens. Verified via the exact same source-inspection technique Package 012 used to prove `dispatcher.py` never imports `argus.workflow` - the test still passes, unchanged in spirit, after this refactor.

A near-miss during implementation: `CapabilityRegistry.register()` needs to validate that a `"workflow"`-kind capability has a `workflow_id`, and the first draft did this by importing `WorkflowAction` from `argus.dispatcher.action` to read `WorkflowAction.kind`. That created a genuine circular import - `argus.capability.registry` -> `argus.dispatcher.action` -> `argus.capability.capability` (since `build_action_from_capability` needs `Capability`) - caught immediately by a smoke-test import, before any tests were written against it. Fixed by using a local string constant (`_WORKFLOW_ACTION_KIND = "workflow"`) instead, documented as tracking `WorkflowAction.kind`'s value by convention rather than by import. This reinforced, concretely rather than just by design intent, that the dependency direction really is one-way: `argus/dispatcher/` depends on `argus/capability/`, never the reverse.

The second real design question: `IIntentDispatcher.resolve()` already existed (Package 012), returning an `Action`. Changing it to return a `Capability` instead is a breaking interface change - deliberate, and explicitly authorized by this package's own "Modify Package 012 only where necessary" instruction, since the work order's own vocabulary ("Dispatcher responsibilities become: resolve capability...") maps directly onto keeping the method name `resolve()` while changing what it resolves *to*. `register_mapping()`/`remove_mapping()`/`list_mappings()` were removed from `IIntentDispatcher` outright rather than kept as a redundant, competing way to register capabilities alongside `ICapabilityRegistry.register()` - two ways to do the same thing would have reintroduced exactly the kind of duplicate-source-of-truth risk this codebase has been careful about since the `ServiceDescriptor`/`LifecycleManager` state duplication was resolved in Package 005's own architectural revision.

`find_by_intent_type()` deliberately returns every match, enabled or not - no selection policy, no filtering. That policy (first enabled match, in registration order) lives entirely in `IntentDispatcher.resolve()` instead, keeping `CapabilityRegistry` a pure metadata store exactly as instructed ("The registry performs NO execution") and matching this package's own explicit architectural guidance that the *Dispatcher*, not the Registry, "resolves capabilities."

Two new events, `CapabilityRegistered`/`CapabilityUnregistered`, were added by direct analogy with `KnowledgeService`'s `KNOWLEDGE_CREATED`/`KNOWLEDGE_DELETED` (Package 006) - the nearest precedent for a metadata CRUD core service publishing lifecycle events for its own register/unregister operations. Considered and rejected a third new event for "capability resolved," distinct from the existing `ActionResolved` - since capability resolution and Action construction happen as one logical step from any caller's perspective, `ActionResolved`'s payload simply grew a `capability_id` field instead, honoring the work order's explicit "Do not introduce unnecessary events."

Whether `CapabilityRegistry` should adopt `IService` was a real question, not a formality - the work order's own BOOTSTRAP section just says "Register the Capability Registry as a Core Service," without specifying. Applied ADR-0002's proposed criterion directly: `register`/`unregister`/`get`/`find_by_intent_type`/`list_capabilities`/`contains` are all fully usable the instant the registry is constructed, with nothing for `start()`/`stop()` to meaningfully gate - architecturally identical to Knowledge Service and Memory Service, both of which deliberately abstained for the same reason. Decided against adoption, and appended this as a new kind of ADR-0002 data point: not a sixth adopter, but the first new deliberate *non*-adopter since Memory Service, evidence that the criterion works as a design-time filter rather than only a post-hoc classification of packages that already implemented `IService` regardless.

## Package 015 - Planner

Built the layer the target architecture diagram inserted above Intent and the Capability Registry: `Planner`, a reasoning-only service that converts an Intent into an ordered, inspectable `Plan` of `PlanStep`s - with no execution, no dispatch, and no plugin awareness anywhere in the package.

The central design tension, immediately visible in the diagram itself: if the Planner sits *above* Intent and the Capability Registry conceptually, does it also need to be *constructed* before them in `bootstrap.py`? Resolved by re-applying the exact distinction Package 013 already established for Capability Registry versus Intent Dispatcher: diagram position describes conceptual data flow, not dependency order. `Planner.validate_plan()` needs a live `ICapabilityRegistry` reference to do its one job (check that a required capability id currently exists), so `Planner` is constructed *last* among the fifteen core services - dependency order, not diagram order, wins every time construction sequencing is in question, a rule now confirmed across two consecutive packages rather than a one-off judgment call.

The second real design question, not spelled out anywhere in the work order's Domain Model: does `PlanStep.order` need active bookkeeping, or is it purely derived from tuple position? Chose active-but-derived: `order` is a real field (as the work order explicitly lists it), but every Planner method that changes a Plan's steps - `add_step()`, `remove_step()`, `reorder_steps()` - recomputes every affected step's `order` to match its actual position, and no public method lets a caller set `order` independently. This was a deliberate ADR-0002-adjacent choice: letting `order` and tuple position potentially diverge would have reintroduced exactly the "two trackers of the same fact" risk this codebase eliminated for `ServiceDescriptor`/`LifecycleManager` back in Package 005's own architectural revision - a risk worth actively avoiding in new code, not just in retrospective analysis.

The third design question, arguably the most consequential: what should happen to a Plan's `status` when its steps change after it was already validated? Nothing in the work order says explicitly. Decided that any structural mutation resets `status` to `CREATED`, reasoning forward from what `VALIDATED`/`FAILED` are supposed to *mean* - a claim about the Plan's *current* steps, which becomes false the instant those steps change. Leaving a stale `VALIDATED` status on a Plan whose steps had since been edited would be a silent correctness bug waiting to surface in whatever future package actually consumes a Plan's status to decide whether it's safe to act on. Requiring re-validation after every structural change costs nothing in Version 1 (nothing executes a Plan yet) and prevents that bug by construction.

Event design required picking apart the work order's own suggested examples rather than adopting all four verbatim: `PLAN_CREATED`, `PLAN_VALIDATED`, `PLAN_UPDATED`, and `PLAN_REMOVED` were offered, but this package's actual Planner responsibilities list has no "delete an entire Plan" operation - only step-level add/remove/reorder. Rather than force a fourth event with nothing to fire it, or invent a redundant one, folded all three step-mutation operations into a single `PLAN_UPDATED` event with a `"change"` payload field distinguishing them - fewer event types, same observability, and no orphaned event name. Considered whether a failed `validate_plan()` call deserved its own "PlanValidationFailed" event, by analogy with `WorkflowEngine`'s and `IntentDispatcher`'s paired `*_FAILED` events, and decided against it: `validate_plan()` is architecturally closer to `CapabilityRegistry.register()`'s or `PluginManager.register()`'s single validation gate than to a multi-step execution engine, so the simpler, already twice-established "failure raises, publishes nothing" precedent applies instead.

Whether `Planner` should adopt `IService` was, again, a genuine question rather than a formality, and this package pushed the criterion further than Package 014's finding did: `validate_plan()` is the closest thing to "real work" any non-adopter has performed so far (an actual registry lookup plus a status transition, not just a dictionary read), which made it worth explicitly checking whether that crossed ADR-0002's line. It doesn't - there is still no "Planner must be started before this works" precondition anywhere, and the work order's own Objective ("It performs reasoning only") rules out anything resembling a background phase by design, not merely by current implementation choice. Appended as the third consecutive non-adopter finding to ADR-0002, now explicitly framing ArgusOS's core services as splitting into two durable categories: metadata/reasoning stores (the growing majority) and a small, stable set of genuinely phased engines identified as early as Package 008.

## Package 016 - Agent Runtime

Built the layer the target architecture diagram inserted between Execution Plan and the Dispatcher: `AgentRuntime`, the only component in ArgusOS permitted to actually execute a Plan - by dispatching its steps, one at a time, through the existing, unmodified `IIntentDispatcher`.

The first real design question surfaced immediately from the work order's own explicit constraints, and had no obvious answer at first glance: "No concurrent execution" is required, but the Runtime API also asks for `pause_execution()`/`resume_execution()` as real, testable operations. How can anything meaningfully "pause" a synchronous, single-threaded loop with nothing else running to call `pause_execution()` from? The resolution came from taking "no concurrency" literally rather than trying to work around it: `start_execution()` runs its entire step loop synchronously in one call, and the *only* way `pause_execution()`/`cancel_execution()` can affect a still-`RUNNING` Execution is a **reentrant** call - one of the Execution's own dispatched steps calling back into the Runtime before its own `dispatch()` call returns. This is fully single-threaded (no concurrency introduced anywhere) but genuinely reentrant, and it turned out to be exactly the mechanism needed to write real, non-contrived tests for pause and resume - not a workaround, but the one physically coherent design given the stated constraints. Getting this right required a second pass on `_run()`'s loop: the first draft blindly advanced `current_step`/`results` after every successful `dispatch()` call, which would have silently clobbered a reentrant pause/cancel that happened *during* that same step's dispatch - fixed by re-fetching the Execution's current stored state before applying the "step completed" update, preserving whatever a reentrant call had already set rather than overwriting it.

The second, more consequential design question: `IIntentDispatcher.dispatch()` takes only an `Intent`, resolving a Capability purely by `IntentType` - but every `PlanStep` names a specific `required_capability` id, and this package's Constraints explicitly forbid modifying Dispatcher's responsibilities. There is no way, without touching Dispatcher, to make `dispatch()` honor a step's specific capability id rather than whatever the Plan's own originating `IntentType` would resolve to. Rather than quietly working around this (which would have meant reaching into `argus.capability.registry` directly - a much bigger boundary violation - or inventing a new Dispatcher method, forbidden outright) chose the option that keeps every explicit constraint intact: construct a synthetic `Intent` per step reusing the Plan's own `IntentType`, pass the step's real `required_capability` id through `dispatch()`'s existing `context` parameter for traceability, and document plainly that Version 1 cannot honor per-step capability targeting as a result. This is a genuine, load-bearing limitation - multi-step Plans whose steps reference *different* capabilities will not behave as their step-level metadata implies - but it's the correct call given the actual constraints in front of this package, and it's now explicit and traceable rather than silently wrong.

The third design question, this time about state ownership rather than mechanics: should `start_execution()` trust the `Plan` object a caller passes in, or re-verify it against the Planner's own live record? Chose to re-fetch: `start_execution()` calls `IPlanner.get_plan(plan.id)` and requires the *canonical* record's status to be `VALIDATED`, using the canonical record's own `steps` for the actual run - not the possibly-stale object the caller is holding. This gives real, functional meaning to the Bootstrap section's explicit "Runtime depends on Planner" instruction (which otherwise would have had no code-level justification, since `start_execution(plan)` already receives a full `Plan` object and wouldn't otherwise need a live Planner reference at all), while staying strictly within "shall NOT validate Plans" - this is a read of already-computed state, never a call to `validate_plan()` itself.

Whether `AgentRuntime` should adopt `IService` was, for the first time in three packages, an easy call rather than a genuine judgment call: "The Runtime owns execution only" is about as direct a signal as ADR-0002's criterion could ask for. `start_execution()`/`resume_execution()` are gated on `RUNNING`, exactly mirroring `WorkflowEngine.execute()`/`ConversationManager.receive()`/`IntentDispatcher.dispatch()`; `pause_execution()`/`cancel_execution()`/`get_execution()`/`list_executions()` stay ungated, mirroring `Scheduler.pause()`/`resume()`'s already-established precedent for per-item operations that don't imply anything about the owning service's own lifecycle. This breaks the three-consecutive-non-adopter streak (013, 014, 015) - appended to ADR-0002 as the clearest evidence yet that the criterion cuts both ways: it doesn't default to "no," and it doesn't default to "yes" just because a package sounds important - it tracks whether `start()`/`stop()` would gate real, distinct work, and here they clearly do.

Verified this didn't affect anything substantive - the file-level state was correct, matching the tag - and proceeded, flagging the process variation rather than treating it as a blocker, since every actual pre-flight check (Package 015 present, tests passing, `main.py` clean, version constant correct) passed cleanly.

## Package 017 - Connector Framework

Built the layer the target architecture diagram appended below Services: `ConnectorManager`, a registry-and-invocation service isolating every external-system call behind one common `IConnector` interface - with, per this package's own explicit instruction, no real integrations anywhere in Version 1, only an in-memory `MockConnector`.

The first real design question came from the package's own file list rather than from any domain ambiguity: `argus/connectors/{__init__,connector,manager,interfaces,exceptions}.py` names exactly five files, with no obvious home for a concrete `IConnector` implementation - yet "Use mock connectors only" requires shipping one. The instinctive place to put it, `connector.py`, turned out to be a trap: `MockConnector` needs `IConnector` from `interfaces.py`, and `interfaces.py` already needs `Connector` from `connector.py` to type `IConnectorManager`'s methods - a straightforward circular import the moment both live in the same file, or in two files that both need each other. Resolved by putting `MockConnector` in `manager.py` instead, which already sits at the top of the package's own dependency chain (nothing inside `argus.connectors` depends on it) - keeping `connector.py` a pure, dependency-free leaf, matching the same "leaf model" shape `Capability`/`Plugin`/`Plan`/`Execution` all already have.

The second design question, not spelled out anywhere in the work order: how does `ConnectorManager` relate `Connector` (metadata) to the actual behavior that backs it? The Connector Model section lists only descriptive fields - no "implementation" or "handler" field anywhere - which meant `Connector` itself couldn't hold a live callable reference without inventing a field the work order never asked for. Settled on two parallel internal dictionaries inside `ConnectorManager`, both keyed by the same `connector.id`, kept in sync on every register/unregister call - `register_connector(connector, implementation)` taking both as separate arguments. This mirrors the existing precedent of keeping value objects free of live service references (`Execution.plan_id` references a `Plan` by id only, never by holding one), just applied for the first time to a case where the *manager itself* needs two different kinds of thing per key, not just one.

The third design question turned out to be the most consequential, because the work order left an internal contradiction to resolve rather than a gap to fill: `ConnectorManager`'s own method list names only `invoke()` - no `connect()`/`disconnect()` at the manager level at all - while `IConnector`'s suggested methods include both. If a caller only ever uses `ConnectorManager`'s public API, there is no way for them to ever call `connect()` on anything directly, yet a connector needs to *become* connected somehow before `invoke()` will do anything meaningful. Rather than leaving this open (which would have made `invoke()` untestable against anything but a connector that happens to already be connected) decided that `invoke()` itself calls the implementation's `connect()` immediately beforehand, relying on `IConnector.connect()`'s own contract requiring idempotency - safe to call whether or not a connection already exists - and deliberately does *not* call `disconnect()` afterward, on the reasoning that "connect once, invoke many times" is the more realistic connection-pooling shape once real (non-mock) connectors exist. This one decision is what makes `MockConnector`'s own "raise if invoked before connect()" branch meaningfully testable at all: reachable directly against a bare `MockConnector` instance (exercised in `tests/test_connector.py`), but never reachable through `ConnectorManager.invoke()` itself, since that path always connects first - a genuine, deliberate asymmetry between the two test files rather than an oversight.

A closely related question followed immediately: should `health_check()` get a `ConnectorManager`-level wrapper too, given "Test: ... health checks" is an explicit required test scenario? Checked the method list again and found the same closed-list signal already used for events in Packages 015/016: `ConnectorManager`'s own bullet list is exactly seven methods, none of them `health_check()`. Rather than adding an eighth method the work order didn't ask for, tested `health_check()` directly against `MockConnector` instances instead - satisfying the explicit test requirement without expanding `ConnectorManager`'s public surface beyond what was actually specified, the same discipline Package 015 applied to `PLAN_REMOVED` and Package 016 applied to pause/resume/cancel events.

Whether `ConnectorManager` should adopt `IService` turned out to be the easiest version of this question the project has faced yet, arguably an even cleaner case than `AgentRuntime`'s (016): `invoke()` is not merely "real work" in the abstract sense ADR-0002's criterion asks about - it is the literal, named boundary between ArgusOS and everything outside it, a stronger case for gating than `IntentDispatcher.dispatch()` (which stays entirely internal) or even `AgentRuntime.start_execution()` (which merely dispatches Intents that stay internal too). Gated `invoke()` on `RUNNING`, left the six registry operations ungated, and appended the seventh adopter/sixth genuinely-gated finding to ADR-0002 - continuing, not breaking, the pattern `AgentRuntime` set in the immediately preceding package.

## Package 018 - Knowledge Graph

Built the layer the target architecture diagram inserted between Planner and Validated Plan: `KnowledgeGraph`, an in-memory semantic layer of `Entity` nodes connected by typed, directed `Relationship` edges - a structured store for persistent knowledge, explicitly not a database, not long-term storage, and not vector search.

The first real design question, not spelled out anywhere in the work order: what happens to a Relationship when one of the two Entities it connects gets removed? Two shapes were on the table - forbid the removal outright while references exist (a foreign-key-style constraint, requiring a new exception and an extra caller step), or cascade the removal (delete every Relationship touching the removed Entity in the same call). Chose cascade: it makes the graph's own referential integrity a structural guarantee rather than something every future caller has to remember to maintain themselves, it costs nothing extra for a caller (no new exception to catch, no required "remove relationships first" step), and it matches "the graph must remain lightweight infrastructure" better than a constraint that would make deletion cumbersome. This paid off directly inside `neighbors()`: because a Relationship can never outlive either Entity it references, the method's own final lookup (`self._entities[other_id]`) never needs a defensive existence check - the invariant `add_relationship()` and `remove_entity()` maintain together makes that branch provably unreachable, not just empirically untested, which is exactly the kind of guarantee this codebase has favored since Package 013's own similar reasoning about `Capability`/`Workflow` id references.

The second design question was really a naming question, but a load-bearing one: the work order's own suggested Relationship fields are `source_entity`/`target_entity`, with no `_id` suffix at all - unlike every other "this field references another model" field in the codebase (`Capability.workflow_id`, `Execution.plan_id`), which always carries one. Followed the established convention over the literal suggestion, naming the fields `source_entity_id`/`target_entity_id` - not just for consistency's sake, but because a `Relationship` holding *live* `Entity` objects would violate this package's own "pure data" requirement and would go stale the instant an Entity got removed and a differently-identified one took its place. This is the same category of deviation already applied to `Execution.id`/`Connector.id` in prior packages: the work order's literal field name loses to established repository convention, documented explicitly rather than silently substituted.

The third design question was the most consequential one in this package, and it's the first of its kind in this project: is `IKnowledgeGraph` extending `IService` a decision to make, or an instruction to follow? Every prior IService question in this codebase - Scheduler, IntentRouter, WorkflowEngine, ConversationManager, IntentDispatcher, CapabilityRegistry, PluginManager, Planner, AgentRuntime, ConnectorManager - was this Engineer's own judgment call, applying ADR-0002's proposed criterion to a work order that left the question open. This one doesn't leave it open: "Create: `IKnowledgeGraph` - Extend `IService`" is explicit. Applying the criterion to the actual methods independently, though, gives a different answer than the instruction does - `add_entity`/`remove_entity`/`get_entity`/`list_entities`/`add_relationship`/`remove_relationship`/`list_relationships`/`neighbors`/`find_by_type` are all synchronous, in-memory, phase-free data operations, architecturally indistinguishable from `CapabilityRegistry`/`PluginManager`/`Planner`'s own non-adopted shape. Resolved this by treating adoption itself as settled (not this Engineer's call to make - the mandate is to implement the specified architecture faithfully, not override it) while still applying the criterion's own logic to the *narrower* question actually left open: which methods, if any, should be gated. The answer there is "none" - gating anything would mean inventing a "must be RUNNING to query" policy nobody asked for, one that would also sit awkwardly against "The Planner may consult the Knowledge Graph" given bootstrap.py's standing "register, never start" rule. This makes `KnowledgeGraph` the second IService adopter in this codebase with zero gated methods, after `IntentRouter` (009) - a precedent that existed and was directly reusable, which made this resolution far more comfortable than inventing a first-of-its-kind shape would have been. Recorded this explicitly in ADR-0002 as a new category of finding: not "does the criterion say yes or no," but "what happens when an explicit instruction and the criterion's own logic point in different directions" - a question worth surfacing for the Founder/Architect rather than quietly resolving in either direction without comment.

The fourth design question came straight from the Architectural Position section's own prose: "The Planner may consult the Knowledge Graph. The Runtime must not modify it." Does *this* package need to actually wire the Planner to consult it? Checked the rest of the work order the same way Package 014's diagram-positioning question was resolved: every substantive section - New Package, Responsibilities, Testing, Documentation, Constraints - describes `KnowledgeGraph` purely as standalone infrastructure, with zero mention of touching `argus/planner/` or `argus/runtime/`. Concluded, as with Package 014's Plugin Manager, that the diagram's arrow describes a capability the target architecture now *permits* for some future package, not a concrete integration this one must build - confirmed afterward by `git diff --stat` showing zero changes outside `argus/knowledge_graph/`, `argus/bootstrap.py`, `argus/events/event_types.py`, and the test/documentation files. "The Runtime must not modify it" ends up trivially satisfied: `AgentRuntime` is never given a `KnowledgeGraph` reference at all in this package.

The fifth and final design question was purely mechanical but genuinely new for this project: the Bootstrap section's construction order (`Capability Registry -> Intent Dispatcher -> Planner -> Knowledge Graph -> Agent Runtime -> Connector Manager`) inserts the new service in the *middle* of the existing sequence, not at the end. Every prior purely-positional insertion (Connector Manager, Package 017) was a simple append; this one required actually moving code - `agent_runtime`'s own construction now needs to come after a new `knowledge_graph = KnowledgeGraph(...)` block rather than immediately after `planner`. Handled by inserting the new construction and container registration between the existing Planner and Agent Runtime blocks, then updating `_register_core_services`'s parameter list, docstring, and `core_services` tuple to match the new order - and re-running the full regression suite immediately afterward to confirm the reordering introduced no behavioral change to `AgentRuntime`'s own dependencies (still `event_bus`/`dispatcher`/`planner`, unchanged), which it didn't.

## Package 019 - Memory Integration

Built the layer the target architecture diagram inserted between Memory Service and the Knowledge Graph: `MemoryIntegration`, a bridge that translates memory records into graph knowledge on demand - "This package owns the bridge - not memory, not knowledge."

The first real design question, and the one that shaped everything else: how does "prevent duplicate graph entities" actually get satisfied, given the Knowledge Graph (Package 018) offers no "does this already exist" convenience beyond `get_entity()` raising `EntityNotFoundError`? The instinctive answer - keep a separate `memory_key -> entity_id` lookup table inside `MemoryIntegration` - felt uncomfortably close to violating "It owns no data itself" the moment it was written down: a lookup table IS a small competing source of truth, even if it only maps ids rather than storing content. Resolved by making the mapping unnecessary rather than trying to justify keeping it: `MemoryMapper` derives every Entity's `id` as a pure function of the memory key alone (`f"memory:{key}"`), so the same key always resolves to the same graph identity, with nothing to look up and nothing that could ever drift out of sync with reality. The `self._synchronized`/`self._failed` dicts `MemoryIntegration` does keep are then honestly just bookkeeping for `synchronization_status()` and idempotency - recoverable at any time from the deterministic scheme alone, not the actual source of truth for anything.

The second design question turned out to be a genuine gap in the Knowledge Graph's own contract, not something this package could route around: the Memory Mapper section explicitly lists `update_entity()` as one of its four responsibilities, but `IKnowledgeGraph` has no update method at all - only `add_entity()`/`remove_entity()` (a closed method list, per Package 018's own precedent of respecting exactly what was asked for). Extending `KnowledgeGraph` itself was off the table - nothing in this package's own New Package listing touches `argus/knowledge_graph/`, and doing so would have blurred exactly the ownership boundary this package's Objective draws so carefully ("not... knowledge"). The resolution that emerged from working through the deterministic-id design above: since the id never changes, "update" doesn't need a dedicated graph primitive at all - remove the old Entity (which cascades away its stale Relationships, a Package 018 behavior inherited for free) and add a fresh one back under the same id. This turned "prevent duplicates" and "synchronize updates" into the same code path rather than two: every `synchronize_memory()` call is a full reconcile, not a conditional branch between "first sync" and "update."

That reconcile-by-remove-then-rebuild design has a real, worth-naming consequence, though, and finding it required tracing through what cascading removal (Package 018's own behavior) actually does to *other* entities, not just the one being resynchronized: if entity C has a Relationship pointing at entity A (C -> A), and A gets resynchronized, removing A cascades away the C -> A edge along with A's own old Relationships - and rebuilding A only reconstructs A's *own* outgoing Relationships from A's current `related_keys`, never anything that pointed *at* A from elsewhere. Resynchronizing A silently drops C's edge unless C is also resynchronized. This isn't a bug so much as the honest cost of the chosen design's simplicity - properly preserving inbound references would require tracking a reverse index for every Entity, real bookkeeping well past "infrastructure only" - so it's documented plainly as a Known Limitation rather than quietly left for someone else to discover, mirroring how Package 016 handled its own synthetic-Intent limitation: name the real cost of the decision, don't pretend it isn't there.

The third design question was about what "translate relationships between memories" could even mean, given `MemoryRecord.value` is untyped `Any` with no relationship concept anywhere in Package 007's own model. Rather than attempting any form of inference - explicitly forbidden ("shall NOT perform graph reasoning") - settled on recognizing exactly one simple, mechanical convention: if `value` is a Mapping containing a `"related_keys"` entry (an iterable of strings), each entry becomes a `Relationship`. This is parsing a known field name, not reasoning, and a record without the convention simply produces no Relationships - the default, unremarkable case, not an error path needing special handling.

The fourth design question surfaced only once the actual implementation began, not during initial design, and was a genuine collision between two of the work order's own instructions rather than an ambiguity to interpret: the Memory Integration Service section lists `status()` as one of five Responsibilities, but this same package is also explicitly instructed to "Extend IService" - and `IService.status()` is a fixed abstract method returning `LifecycleState`, used identically and exclusively for that purpose by every other adopter in this codebase (eight of them by this point). A method literally cannot satisfy both contracts under one name without breaking Liskov substitution for any caller treating `MemoryIntegration` polymorphically as an `IService` - this wasn't a judgment call so much as a genuine impossibility to work around. Resolved by naming the domain method `synchronization_status()` instead, preserving `status()`'s single, consistent meaning everywhere in the codebase - a deliberate, clearly-documented deviation from the work order's literal method name, forced by the work order's own two instructions being mutually incompatible as written, not a preference.

The fifth question, and the most interesting one for ADR-0002 specifically, was whether `IMemoryIntegration` extending `IService` (again an explicit instruction, following Package 018's identical situation) would turn out to be another case where the criterion and the instruction disagree. This time they didn't: `synchronize_memory()`/`synchronize_all()`/`remove_memory()` each genuinely coordinate two separate live systems in a single call - reading `IMemoryService`, writing `IKnowledgeGraph` - architecturally indistinguishable from `AgentRuntime.start_execution()`'s or `ConnectorManager.invoke()`'s own gated shape, if anything a clearer case than either since two dependencies are touched rather than one. Gated those three, left `synchronization_status()`/`reset()` ungated (pure operations over this package's own bookkeeping only), and recorded the finding as the direct counterpart to Package 018's: there, instruction and criterion diverged; here, they agree. Read together, the two packages suggest ADR-0002's own text conflates two genuinely separate questions - whether to adopt `IService` at all (which this project has now seen decided both by explicit instruction and by independent judgment) and which specific methods to gate (which has so far always been this Engineer's own criterion-driven call, regardless of which route led to adoption) - worth flagging for the Founder/Architect as a possible future revision rather than something to resolve unilaterally.

One implementation-time lesson, caught before it became a real problem rather than after: the first version of the new bootstrap-level end-to-end test called `memory_service.put()` directly against `bootstrap()`'s own real, disk-backed `JSONMemoryStorage` (Package 007's own default) without any cleanup - which worked once, then failed on every subsequent run with `DuplicateMemoryError`, and `git status` confirmed why: the test had left an actual modification in the repository's own `memory/memory_store.json`, exactly the kind of unintended repository side effect this project's standing verification discipline exists to catch. ## Package 020 - Reasoning Engine

Built the layer the target architecture diagram inserted between the Knowledge Graph and the Planner: `ReasoningEngine`, a deterministic, read-only query layer that answers structural questions about the graph - "It does not make decisions. It does not execute plans. It performs deterministic reasoning only." Per the work order's own explicit instruction, the Planner does not consume it yet; this package only introduces the service.

The first real design question was the same one Package 018 raised, reaching the same conclusion for a related but distinct reason: is `IReasoningEngine` extending `IService` a decision to make, or an instruction to follow? Again explicit - "Create: `IReasoningEngine` - Extend `IService`" - so adoption itself wasn't this Engineer's call. Applying ADR-0002's criterion to the six actual methods independently, though, gives the same answer Package 018's Knowledge Graph got: `query()`/`neighbors()`/`find_paths()`/`related_entities()`/`entity_summary()`/`relationship_summary()` are all synchronous, read-only, in-memory operations with no phase distinction any of them could plausibly be gated on. Gated none of them, exactly mirroring `KnowledgeGraph`'s (018) and `IntentRouter`'s (009) shape - the third such case in this codebase, and the second (after 018) where an explicit instruction diverges from what the criterion alone would have concluded. Having two directly reusable precedents for this exact shape made the decision comfortable rather than novel this time.

The second design question was new, and took longer to settle than the IService question did: the Bootstrap section explicitly lists Memory Integration as a dependency alongside the Knowledge Graph, and the Objective states the engine "consumes information from the Knowledge Graph and Memory Integration" - stronger, more literal language than Package 018's own "the Planner *may* consult the Knowledge Graph," which that package correctly treated as a future capability and left entirely unexercised. Leaving the injected `IMemoryIntegration` unused here would have contradicted the Objective's own plain text, not just its diagram. The tempting shortcut - reach into `MemoryMapper`'s deterministic `f"memory:{key}"` id scheme to correlate individual graph Entities back to the memory keys that produced them - was rejected on inspection: that scheme is `MemoryMapper`'s own private implementation detail (documented as such in its own module docstring), not part of `IMemoryIntegration`'s or `IKnowledgeGraph`'s public contract, and depending on it here would have created exactly the kind of hidden, fragile cross-package coupling this codebase's interface discipline exists to prevent - plus it would have blurred into "graph reasoning," which this package's own Responsibilities explicitly forbid it from doing (that inference, if it ever happens, belongs to Memory Integration, not here). Settled on the most restrained genuine use available: every public method attaches `IMemoryIntegration.synchronization_status()`'s own whole-system snapshot - already ungated, already read-only, already just a view of that service's internal bookkeeping - to its result's `metadata`, unconditionally. This satisfies "consumes information from... Memory Integration" honestly without inventing any new architecture or correlation logic that wasn't asked for.

The third design question was about what "evaluate simple graph patterns" and the explicit `find_paths()` method actually license, given Package 018's own Knowledge Graph was deliberately built with "no graph traversal algorithms... no shortest path" as an explicit constraint. Read those two packages together rather than in isolation: Package 018's "no graph algorithms *yet*" was a stated deferral to a future package, not a permanent prohibition on the architecture as a whole - and this package's own Constraints list forbids LLMs, probabilistic reasoning, and graph mutation, but conspicuously not graph traversal algorithms, while its Responsibilities explicitly ask for path evaluation. Concluded that Package 020 is the deferred "yet," and implemented two bounded, exhaustive, deterministic traversals rather than anything heuristic: breadth-first reachability (for `query()`'s `entity_id` branch, bounded by an explicit `depth`), and depth-first simple-path enumeration (for `find_paths()`, bounded by an explicit `max_depth`, tracking visited entities so no path repeats a node). Both treat every Relationship as traversable in either direction, deliberately reusing `KnowledgeGraph.neighbors()`'s own established "connected... in either direction" precedent (Package 018) rather than introducing a second, inconsistent traversal semantics for the same edges.

The fourth design question was purely mechanical but shaped a good deal of `query()`'s actual code: how much should the four branches (`entity_id`, `entity_type` alone, `relationship_type` alone, both together) share versus stay separate? Chose separate, explicitly-named private methods per branch (`_query_by_entity_id`, `_query_by_entity_type`, `_query_by_relationship_type`, `_query_by_pattern`) rather than one large conditional tree, on the theory that each branch answers a genuinely different question (a bounded traversal vs. two flavors of type-only search vs. a pattern match) and forcing them into one shared code path would have made each individually harder to verify in isolation - a call this project made once before, in Package 016's runtime for a similar reason, and it held up the same way here: each branch's own test class stayed short and legible.

The fifth design question came directly out of writing the test suite, not the initial implementation: `_other_endpoint()` had a defensive third branch returning `None` for "this relationship doesn't touch the given entity_id at all," left over from writing it generically before checking whether any call site could actually reach that condition. None could - every call site pre-filters through `_relationships_touching()` first, exactly mirroring the invariant Package 018's own `KnowledgeGraph.neighbors()` already relies on (and had its own identical redundant filter removed for, during that package's implementation). Removed the dead branch here for the same reason, rather than writing a contrived test just to exercise unreachable code - the coverage tool caught it as a missing line, and the fix was to simplify the method to what its actual, provable precondition allows, not to invent a test around dead code.

One implementation-time correction, caught by the initial smoke test rather than the formal suite: an early version of `test_relationship_type_filter_restricts_traversal` asserted that filtering `query()`'s `entity_id` traversal to `relationship_type="works_at"` at `depth=2` would exclude Bob entirely - but Bob is legitimately reachable from Alice via `works_at` alone (Bob works_at Acme, and Acme is already in the depth-1 frontier), so the correct behavior includes him. The test's expectation was wrong, not the traversal - fixed by splitting it into a `depth=1` case (direct neighbors only, correctly excluding Bob) and a separate `depth=2` case documenting that the filter restricts *which edges* are followed, not how far a bounded traversal can legitimately reach through them.

## Package 021 - Decision Engine

Built the layer the target architecture diagram inserted between the Reasoning Engine and the Planner: `DecisionEngine`, a deterministic rule-evaluation service that turns one or more `ReasoningResult` objects into a structured `Decision` - "It does not execute decisions. It does not invoke the Planner. It does not use AI or LLMs. Its responsibility is limited to deterministic decision evaluation."

The first real design question was how "No scripting. No Python execution. No dynamic code generation" translates into an actual `DecisionRule` shape. The tempting middle ground - accept rule logic as a small string-based expression language, then write a minimal parser/evaluator for it - was rejected immediately: any parser this package wrote would itself BE a scripting language, just a smaller one, and the constraint reads as a prohibition on the entire category, not merely on `eval()`/`exec()` specifically. Settled on `predicate` being a plain Python callable, supplied directly by the caller at `DecisionRule` construction time - this package never parses, interprets, or dynamically constructs any logic at all; the caller's own Python function IS the rule, and `DecisionEngine` only calls it, deterministically, in priority order. This satisfies the constraint by construction (there is no code path in this package capable of executing arbitrary text as code) rather than by validation trying to detect and reject disallowed patterns after the fact - the same category of design choice as Package 019's `related_keys` convention: recognize a fixed, simple mechanism instead of attempting anything resembling inference or interpretation.

The second design question was what `evaluate()` and `evaluate_all()` are each actually for, since the work order lists both as separate public methods without further elaboration. The Objective's own sentence - "evaluates one or more `ReasoningResult` objects and produces a deterministic `Decision`" - reads naturally as one-or-more inputs producing exactly one output, which is also what `Decision.reasoning_results` (plural) already implies for a single `Decision`. Resolved this as a singular/plural convenience pair, mirroring `MemoryIntegration.synchronize_memory()`/`synchronize_all()`'s (019) shape but adapted for the fact that this package has no natural "list of pending items" the way Memory Service does: `evaluate(reasoning_result, *, decision_type)` handles the single-result case and simply delegates to `evaluate_all((reasoning_result,), decision_type=decision_type)`, which does the actual work - running every registered rule against the full set of results given, never stopping at first match, since `matched_rules` (plural, per the work order's own `Decision` field list) implies the caller wants to know about every rule that matched, not just the first.

The third design question, and the one that took the most iteration to settle, was what `evaluate_all()` should do when a rule's own predicate raises an exception. `MemoryIntegration.synchronize_all()` (019) established a "one failure doesn't abort the batch" precedent for exactly this shape of question - but on reflection that precedent doesn't transfer here, because the two failure categories are not analogous. A `MemoryRecord` failing translation was foreseeable and expected (a `related_keys` reference to a not-yet-synchronized key, for instance) - normal traffic, not a bug. A deterministic rule predicate raising on well-formed `ReasoningResult` input, by contrast, means the predicate itself is broken - a caller-side bug, not an expected outcome this package should quietly route around. Treating it as best-effort (skip the broken rule, keep going) would have silently hidden exactly the kind of error "never silently ignore errors" exists to catch. Settled on the opposite of Package 019's own choice: the first raising predicate aborts the whole `evaluate_all()` call, publishes `DECISION_FAILED`, and re-raises as `RuleEvaluationError` - no partial `Decision` is ever returned. Documented the contrast with Package 019 explicitly in `engine.py`'s own module docstring, since without that context the different choice here could easily look like an inconsistency rather than a considered one.

The fourth design question echoed Package 020's own resolution almost exactly, and landed on the same conclusion for closely related but not identical reasons: is `IDecisionEngine` extending `IService` a decision to make, or an instruction to follow? Explicit again - "Create: `IDecisionEngine` - Extending `IService`" - so, as with Packages 018 and 020, adoption itself wasn't this Engineer's call. Applying the criterion to the six actual methods independently gives the same answer as those two: `evaluate()`/`evaluate_all()` call only local predicate functions and `register_rule()`/`remove_rule()`/`list_rules()`/`decision_summary()` are synchronous registry operations - nothing plausibly gateable. Gated none of them, making `DecisionEngine` the fourth zero-gated adopter in this codebase (after `IntentRouter`, `KnowledgeGraph`, and `ReasoningEngine`) and the third of four consecutive directed-adoption packages to diverge from the criterion's own conclusion (018 diverged, 019 converged, 020 diverged, 021 diverges again) - a pattern solid enough now that the ADR-0002 recommendation to formally separate "adoption" from "gating" feels less like a hunch and more like an observation with real weight behind it.

The fifth design question was the direct counterpart to Package 020's own Memory Integration question, and required working through why the same resolution wouldn't automatically transfer. This package's Bootstrap section explicitly states "Decision Engine depends on: Reasoning Engine," so the constructor genuinely accepts an injected `IReasoningEngine` - but should `DecisionEngine` actually call it anywhere, the way `ReasoningEngine` (020) genuinely called its own injected `IMemoryIntegration.synchronization_status()`? Two things made the honest answer "no" this time, not a shortcut: first, this package's own Objective phrase - "evaluates one or more `ReasoningResult` objects" - describes operating on data the *caller* already supplies, unlike Package 020's own Objective, which explicitly said the Reasoning Engine itself "consumes information from... Memory Integration" as a live service. Second, and more decisively, `IReasoningEngine` simply has no equivalent to `IMemoryIntegration.synchronization_status()`'s zero-argument, whole-system snapshot - every one of its six methods needs a specific, meaningful parameter (an `entity_id`, a `relationship_type`) that `DecisionEngine` has no principled way to supply on its own, blindly, on every `evaluate()` call. Considered attaching the inherited `status()` call just to demonstrate "genuine use," and rejected it quickly: since bootstrap never starts any core service, that call would return `CREATED` on literally every invocation, forever - decorative, not functional, worse than honestly documenting non-use. Left the dependency wired (per the explicit instruction) but uncalled, and named this a third distinct shape in this codebase, alongside Package 018's "not wired at all" and Package 020's "wired and genuinely used."

## Package 022 - Cognitive Context

Built the layer the target architecture diagram inserted between the Reasoning Engine and the Decision Engine: `CognitiveContext`, an immutable transport object that carries one reasoning cycle's accumulated state forward - "It represents the complete state of a reasoning cycle... It does not perform reasoning. It does not make decisions. It does not execute plans. It is a transport object only." Per the work order's own explicit instruction, neither the Decision Engine nor the Planner consume it yet; this package only introduces the abstraction.

This package's first, and most consequential, design question was genuinely new in kind, not just in content: every prior package since 013 has settled "is this an `IService`?" either by explicit instruction or by applying ADR-0002's criterion - but this package's own work order settles a different, more fundamental question outright: "This is not an IService... This package intentionally introduces no new core service." There was no criterion to apply and no divergence to weigh, because the question of adoption itself was answered before implementation began, the same way "IDecisionEngine extends IService" settled Package 021's own adoption question - just answered in the opposite direction this time. The practical consequence touched nearly every file this package would normally have modified: no `bootstrap.py` construction, no Container registration, no Lifecycle Manager entry, no `CORE_SERVICE_NAMES` sync in either `tests/test_bootstrap.py` or its stray duplicate. `ICognitiveContextBuilder` extends plain `ABC` instead - and, usefully, this project already had a directly reusable precedent for exactly that shape: `IConnector` (017), the one interface in this codebase that is "plain behavior, not a lifecycle-managed service," sitting alongside `IConnectorManager`, which does inherit `IService`. Recognizing that `ICognitiveContextBuilder` belongs in `IConnector`'s category rather than `IConnectorManager`'s made the "no IService" instruction feel like an application of an existing pattern rather than an unprecedented one.

The second design question was about the four fields the work order calls "references" - `memory_references`, `knowledge_references`, and `decision_references` - versus `reasoning_results`, the one field whose name doesn't use that word. Two shapes were genuinely on the table: hold the live objects for all four fields (an `Entity`/`Relationship`/`Decision` is already immutable, so nothing prevents it structurally), or hold bare identifier strings for three of them and live objects only for `reasoning_results`. Chose the asymmetric shape, for a reason rooted in the work order's own word choice more than in any technical necessity: the work order's field list itself draws exactly this line - three fields named "...references," one field named "...results" - and reading that as deliberate rather than incidental, holding only identifier strings for the three reference fields is what makes two of this package's own Constraints true *by construction* rather than by discipline: "shall NOT modify any contained object" (a string has nothing to modify) and "shall NOT own persistence" (a string is not an object graph requiring anyone's persistence strategy). It also avoids a coupling this codebase has consistently declined to introduce - `CognitiveContext` importing `argus.memory_integration`'s or `argus.knowledge_graph`'s own concrete value-object shapes just to hold references to them, the same category of restraint `ReasoningEngine` (020) showed when it explicitly declined to reach into `MemoryMapper`'s private id scheme rather than adding a new cross-package dependency for a convenience.

The third design question was how to reconcile the work order's two separate descriptions of "metadata" - the Responsibilities section's "arbitrary metadata" (open-ended, caller-supplied) against the dedicated Metadata section's specific named fields ("creation timestamp, version, correlation identifier"). Read in isolation, each description alone would suggest a different, incompatible shape for `ContextMetadata`: a bare `Mapping[str, Any]` for the first, a small fixed-field value object for the second. Rather than adding two separate metadata-shaped fields to `CognitiveContext` to satisfy both literally, combined them into one: `ContextMetadata` holds `created_at`/`version`/`correlation_id` as named, system-assigned fields, plus one `extra: Mapping[str, Any]` field that `ContextBuilder.with_metadata()` is the only way to populate. This reading treats the Metadata section's "such as" phrasing (implicitly non-exhaustive) as the reconciling detail - the three named fields are the common case worth naming explicitly, `extra` is the genuinely arbitrary part the Responsibilities section separately promised.

The fourth design question was about `ContextBuilder`'s own accumulation semantics, and it's the first time this codebase has built a deliberately mutable class at all - every prior "builder-shaped" component (`DecisionEngine`'s rule table, `ConnectorManager`'s registry) is a full `IService`, not a bare accumulator with no lifecycle. "The builder is mutable. The resulting context is immutable" settled the big question (mutate the builder, freeze the output) but left a smaller one open: should `with_memory()` called three times *replace* the accumulated list each time, or *append* to it? Chose append, for `with_memory()`/`with_knowledge()`/`with_reasoning()`/`with_decision()` - a replace-only builder wouldn't really need "fluent chaining" to be meaningful at all, since a caller could just pass the final list once; accumulation is what makes calling the same method multiple times across a pipeline's several stages (Reasoning Engine appending its own results, Memory Integration appending its own references, and so on, in a future package) a sensible pattern to build toward. `with_conversation()` is the deliberate exception: `conversation_id` is a single scalar, not a collection, so repeated calls overwrite - last call wins, the same rule applied to a repeated `with_metadata()` call using an identical key.

The fifth design question was where validation should actually live, given `CognitiveContext` has no consuming service the way `Entity` has `KnowledgeGraph.add_entity()` or `DecisionRule` has `DecisionEngine.register_rule()`. Every value object in this codebase performs zero validation of its own - that discipline held here too, for the same reason it always has: a pure data holder shouldn't police its own construction, and this package's own "no lifecycle, no service" nature makes that even more clearly correct, since there is no natural place inside `CognitiveContext` itself for a validation policy to live. `ContextBuilder` took on that role instead, purely because it's the one place in this package that already does something *before* constructing a `CognitiveContext` - not because it is, in any formal sense, a "service" the way `KnowledgeGraph` or `DecisionEngine` are.

## Package 023 - Planning Session

Built the layer the target architecture diagram inserted between the Cognitive Context and the Planner: `PlanningSession`, an immutable transport object that represents a single planning cycle - "It performs no planning. It executes no workflows. It is a transport object only." Per the work order's own explicit instruction, the Planner does not consume it yet; this package only introduces the abstraction, the second consecutive package (after 022) to do so.

The first design question was already half-answered by Package 022's own precedent, and resolving it was mostly a matter of confirming the precedent actually transferred rather than discovering something new: is `IPlanningSessionBuilder` extending `IService` a live question here? No - "This is not an IService... No service registration. No lifecycle integration. No EventBus changes" settles it identically to Package 022's own "This is not an IService" instruction, in the same direction. Having a directly reusable precedent from the immediately preceding package (rather than reaching back to Package 017's `IConnector` alone) made this the most comfortable version of this question this project has faced yet - no new reasoning was required, only confirming that `IPlanningSessionBuilder` belongs in the same "plain behavior, not a lifecycle-managed service" category `ICognitiveContextBuilder` already established.

The second design question was the interesting one, and it's the direct inverse of Package 022's own defining design choice. Package 022's `CognitiveContext` deliberately holds three fields (`memory_references`/`knowledge_references`/`decision_references`) as bare identifier strings rather than live objects, reasoning from the work order's own field-naming distinction between "...references" and "...results." This package's own work order draws no such distinction anywhere - `cognitive_context`, `goals`, and `constraints` are simply named for what they are, with no "reference" language attached to any of them - and `PlanningSession`'s Immutable fields list reads the same way `Decision.reasoning_results`/`matched_rules` (Packages 020/021) already do: the actual objects, held directly. Resolved by holding live objects throughout - `cognitive_context` is the actual `CognitiveContext` (Package 022) instance, `goals`/`constraints` hold actual `PlanningGoal`/`PlanningConstraint` objects - and confirmed this didn't quietly violate "shall NOT mutate contained objects" by checking what holding a live `CognitiveContext` actually costs: nothing, since `CognitiveContext` is itself already fully immutable. The same Constraint that Package 022 satisfied by holding bare strings (nothing to mutate) is satisfied here by a different route (an object that structurally cannot be mutated) - useful confirmation that "hold references" and "hold live objects" aren't actually in tension with that Constraint at all; the real deciding factor is just whether the referenced/held type happens to be mutable, and `CognitiveContext` happens not to be.

The third design question was, again, a direct reuse rather than a fresh problem: how to reconcile this package's own two separate descriptions of "metadata" - the Responsibilities section's generic "metadata" against the dedicated Planning Metadata section's named fields ("creation timestamp, version, correlation identifier"). This is word-for-word the same tension Package 022's own Metadata section presented, and `PlanningMetadata` resolves it by directly copying `ContextMetadata`'s own shape: three system-assigned named fields plus one open `extra` mapping that `with_metadata()` alone populates. Worth naming explicitly now that it's happened twice in a row: this isn't a coincidence of two similarly-worded work orders so much as a genuine, reusable answer to "how do you model a value object whose own spec names both specific fields and an open-ended 'metadata' responsibility" - any future package facing the identical wording should very likely reach for the same shape without re-deriving it from scratch.

The fourth design question was mechanical but worth getting right: `PlanningGoal.priority` is explicitly "descriptive only. No scheduling logic," which raises the question of what `PlanningSession.goals`' own ordering should actually be, given a `priority` field exists right there on each element. Resolved by making `goals` a pure append-ordered sequence - `PlanningSessionBuilder.with_goal()` never sorts, and `PlanningSession` never re-orders its own `goals` tuple by `priority` at construction time either. This is a deliberate contrast with `DecisionRule.priority` (Package 021), which `DecisionEngine.list_rules()` actively sorts by - the two `priority` fields share a name and a type but have entirely different behavioral weight, and the work order's own "descriptive only" language for this package is exactly what makes that difference intentional rather than an inconsistency worth flagging.

The fifth design question, field ordering for `PlanningGoal`/`PlanningConstraint`, was a direct rerun of a now-familiar mechanical pattern: the work order lists `goal_id` before `name`, and `constraint_id` before `name`, but `name` has no sensible default (an unnamed goal or constraint isn't meaningful) while `goal_id`/`constraint_id` both default to a fresh uuid4 - so both dataclasses had to place `name` first in actual declaration order, the same "required fields before defaulted fields" reordering already applied to `Entity`, `ReasoningQuery`, and `DecisionRule` in every prior instance of this exact tension.

## Package 025 - Cognitive Pipeline

The first design question was what "the existing Conversation object" in the work order's own PipelineRequest description actually referred to, since no class in this codebase is literally named `Conversation`. ## Package 027 - Response Engine

Built the layer that closes the loop on "cognitive output" as this codebase's own vocabulary has used the phrase since Package 025: `ResponseEngine`, which converts a validated Plan into a `Response` - a standardized, non-AI, non-rendered contract sitting immediately after the Planner in the target architecture diagram. "The Response Engine converts a validated Plan into a structured response object... Its responsibility is to transform cognitive output into a standardized response contract." This package also did something no prior package in this phase has: it amended an already-shipped package's own public contract - `AgentResponse.pipeline_result: PipelineResult` (Package 026) is renamed and retyped to `AgentResponse.response: Response`, a genuine breaking change, not an additive one, per this package's own explicit "Agent Integration" instruction.

The first design question was what `ResponseEngine`'s own constructor should look like, and it turned out to have an answer unlike anything else in this codebase: nothing. "ResponseEngine may depend only on: Plan" - and Plan is not a live service to inject, it is the one argument `build_response()` itself takes. Every other core service in this codebase, including every zero-gated `IService` adopter before it (`IntentRouter`, `KnowledgeGraph`, `ReasoningEngine`, `DecisionEngine`), holds at least one constructor dependency, typically an `IEventBus`, even when nothing in its own domain methods ever calls into it. Recognizing that `ResponseEngine.__init__()` should take zero parameters wasn't obvious until actually trying to write it with an `event_bus` parameter out of habit and then asking what it would ever be used for - the honest answer was "nothing," which is exactly what "No event publication" and "may depend only on: Plan" already say plainly, if read literally rather than through the lens of every prior package's own shape.

The second design question was whether `build_response()` should be gated on `RUNNING`, and applying ADR-0002's criterion here was the most clear-cut case this codebase has faced yet: a method with no live collaborator to coordinate simply has nothing gate-worthy to protect. `ResponseEngine` is now the fifth zero-gated `IService` adopter (after `IntentRouter`, `KnowledgeGraph`, `ReasoningEngine`, `DecisionEngine`) and the fourth case where an explicit instruction to adopt `IService` diverges from what the criterion alone would conclude (after Packages 018, 020, 021) - breaking the exact three-divergent/three-convergent tie Package 026's own finding had just established, back toward divergent, four to three across seven directed-adoption data points. `design/decisions/0002_ISERVICE_ADOPTION_CRITERION.md` gained a new Empirical Finding recording this, and explicitly noting that the sequence so far (018-div, 019-conv, 020-div, 021-div, 025-conv, 026-conv, 027-div) shows no discernible pattern in either direction - the strongest evidence yet for the standing recommendation that "adoption" and "gating" are genuinely separate questions.

The third design question was what `Response.status` should actually be, given `Response` already holds the full `plan` object directly - `plan.status` is right there. Read the work order's own four-field list (`response_id`, `plan`, `status`, `metadata`) literally rather than treating `status` as redundant and dropping it: `ResponseEngine.build_response()` copies `plan.status` into `Response.status` explicitly at construction time, giving `Response` a standalone field mirroring `Plan`'s own without deriving it via a computed property - the same explicit-field-even-where-it-overlaps choice `PlanningSession` (Package 023) already made by holding a live `CognitiveContext` directly rather than only a derived identifier.

The fourth design question was what `ResponseMetadata` should actually mirror, given the work order's own explicit instruction: "Include: timestamp, version, correlation_id. Mirror the style used throughout ContextMetadata and PlanningMetadata." Read both parts literally rather than reconciling them into one: the *shape* (three named fields plus an `extra` mapping, all the same defaults and wrapping) mirrors `ContextMetadata`/`PlanningMetadata` exactly, but the first named field is spelled `timestamp` here, not `created_at` like both precedents use - a small, deliberate, explicitly-flagged deviation rather than a silent normalization to match the two modules it otherwise copies verbatim.

The fifth design question was where `ResponseMetadata.extra` should get its data from, given `ResponseEngine` "may depend only on: Plan" - it has no access to whatever metadata the original `AgentRequest`/`PipelineRequest` carried; that propagation chain terminates at `PipelineResult.metadata` (Package 025), one layer above `ResponseEngine` in Version 1's actual call graph. The one metadata source genuinely available to it is `plan.metadata` itself - which, via `Planner.plan_session()`'s own `_session_plan_metadata()` (Package 024), already carries `planning_session_id`/`cognitive_context_id`/`constraints` forward. `build_response()` copies `dict(plan.metadata)` into `Response.metadata.extra` unchanged - a genuine, testable propagation path using only the one dependency this package is allowed to have, even though it necessarily carries a narrower set of keys than what `AgentResponse.metadata` itself still shows directly, one layer up.

The sixth and most consequential design question was how to make "Return AgentResponse now containing: Response instead of: PipelineResult" concrete. ## Package 028 - Execution Trace

Built the layer this codebase's own vocabulary has been implicitly missing since the very first Cognitive Pipeline package: a first-class record of how a single request actually moved through Argus, independent of what any individual stage produced. "The Execution Trace is an immutable record of how a request moved through Argus. It is not logging. It is not debugging. It is not telemetry. It is a first-class architectural object." `ExecutionTrace` sits in the diagram between `Agent Service` and `Pipeline` - "The Execution Trace accompanies the request from beginning to end" - and, unlike every package since 024, this one introduces no new core service at all: "No new core services. TraceBuilder is not a service."

The first design question was what shape `TraceStep` and `TraceMetadata` should take, and both answers came directly from precedent rather than invention. `TraceStep.component`/`.action` are open strings, not a closed enum, because the work order's own phrasing - "Example component values: AgentService, CognitivePipeline, Planner, ResponseEngine" - says "Example," not an exhaustive list, mirroring `PlanStep.step_type`'s own open-string precedent. `TraceMetadata` mirrors `ContextMetadata`/`PlanningMetadata`'s shape and field names exactly (`created_at`, `version`, `correlation_id`, `extra`) - this package's own explicit field list spells the timestamp field `created_at`, reverting to the two-package-old convention rather than repeating `ResponseMetadata`'s (Package 027) one-field `timestamp` deviation. `extra` itself is not named in this package's own field list either, exactly as it wasn't in Package 027's - included anyway, the same reasoning applied both times: every sibling metadata class ends with one, and `TraceBuilder.with_metadata()` needs somewhere to accumulate into.

The second design question was what `TraceBuilder`'s own fluent API should look like, resolved by reading `ContextBuilder`/`PlanningSessionBuilder` (022/023) as the direct template rather than inventing a new shape: `with_step(component, action, metadata=...)` validates and appends, in call order, the same "accumulate, don't overwrite" rule every prior builder's collection fields already use; `with_metadata(key, value)` accumulates into `TraceMetadata.extra` with last-call-wins on repeated keys, the identical rule `ContextBuilder`/`PlanningSessionBuilder`'s own `with_metadata()` already establishes; `build()` returns an independent snapshot, callable more than once without mutating an earlier one. One choice with no direct precedent to copy: `trace_id` is generated once, in `__init__`, not regenerated on every `build()` call - so that multiple snapshots taken from the same builder as more steps accumulate all describe the same logical trace, sharing one identity, rather than looking like unrelated traces each time `build()` runs.

The third and by far the most consequential design question was a genuine tension inside the work order itself, between two of its own sections. The Integration section's own arrow diagram lists steps in this literal order: create TraceBuilder, record AgentService entry, Pipeline, record Pipeline completion, Response Engine, record Response completion, build ExecutionTrace - "build ExecutionTrace" listed dead last, after Response Engine has already been invoked. But the Dependency Rules section states, unconditionally: "ResponseEngine shall not construct traces. It receives the finished trace." Read with total literalness, the diagram's own ordering would mean the trace `ResponseEngine` "receives" is not yet built at the moment it receives it - a direct contradiction, since a trace cannot simultaneously be "finished" and "not yet built." Several readings were considered - building the trace twice and swapping it into the returned `Response` via `dataclasses.replace()` after the fact, or treating the diagram as strictly authoritative and accepting the contradiction as unresolvable - and rejected: the first would have `AgentService` itself constructing/modifying `Response` instances, a responsibility this codebase has never given anything but `ResponseEngine`; the second isn't actually an option, since shipping code has to pick one behavior. The Dependency Rule - phrased as "shall/shall not," this codebase's strongest form of instruction - took precedence over the diagram's own literal arrow ordering, read instead the way every prior package's own "Architectural Position" diagram has been read throughout this project: as a narrative summary of the stages involved, not a strict line-by-line call sequence. Concretely, the step the diagram calls "record Response completion" is recorded as `("ResponseEngine", "invoked")`, immediately *before* `build_response()` is called, not after - an honest description of what has actually occurred at the moment it is recorded ("the trace records that a stage occurred, not its internal reasoning" - labeling something "completed" before it has completed would misrepresent what happened). This keeps the trace genuinely finished and immutable at the exact moment `ResponseEngine` receives it, honors the Dependency Rule literally, and still records all three example component values this package's own `step.py` names, in the finished trace `Response.execution_trace` ultimately exposes to every caller.

## Package 029 - Task Model

Built the first piece of vocabulary this codebase has ever had for "one thing that needs to happen" independent of the Planner's own `PlanStep` - `Task`, an immutable value object explicitly scoped to describe work, never to perform, schedule, or dispatch it. "A Task represents a single unit of work produced by a Plan. This package introduces no execution. Only the model." The first design question was what shape `Task` itself should take, given the work order names five fields (`task_id`, `name`, `description`, `status`, `metadata`) but gives no explicit guidance on which are required. `PlanStep` - this codebase's closest existing analogue, "one unit of work" one layer up - makes `description`/`required_capability` required with no default, since `PlanStep` is constructed directly by `Planner.add_step()`, with no builder of its own. `Task`, by contrast, gets its own dedicated `TaskBuilder` - the same shape `CognitiveContext` (022), `PlanningSession` (023), and `ExecutionTrace` (028) all share, and in every one of those three, every field defaults, leaving the builder (not the bare dataclass) as the place validation actually happens. ## Package 031 - Task Relationships

Built the first way for one `Task` to describe a connection to another: `TaskRelationship`, a new standalone value object holding a `source_task`, a `target_task`, and a `relationship_type` drawn from a closed four-member enumeration - `PRECEDES`, `FOLLOWS`, `RELATED`, `BLOCKS` - with zero behavioral consequence attached to any of them. The second design question was a near-exact repeat of one Package 029 already answered: `RelationshipBuilder`'s own four-item Responsibilities list ("create relationship, assign metadata, assign type, build immutable TaskRelationship") never separately names "assign source_task"/"assign target_task," the identical shape of gap `TaskBuilder`'s own "create task" bullet left around `with_name()`/`with_description()`. The third design question had no real precedent to lean on: what should `RelationshipType`'s own default be? `TaskStatus` has an obvious answer - `PENDING`, the literal starting state of any Task's own lifecycle - but nothing about "the starting state of a relationship" is inherent to four inherently peer-level, non-sequential enum members. Resolved by reading the members themselves: `PRECEDES`/`FOLLOWS`/`BLOCKS` all carry some directional or prescriptive flavor in natural language (even though none of them actually behaves that way in code - "Do not interpret them" applies to this codebase's own code, not to how a human reads the member names), while `RELATED` reads as the one genuinely neutral, non-committal member. `RelationshipType.RELATED` became the default on that basis - a judgment call with no work-order text to point to directly, flagged explicitly as such in this package's own documentation rather than presented as though the work order had specified it.

The fourth and most structurally interesting problem wasn't a design ambiguity at all - it was a genuine circular dependency the work order's own two integration instructions create together. "Create immutable: TaskRelationship. Fields: ... source_task, target_task ..." requires `TaskRelationship` to import `Task`. "Extend immutable: Task. Add: relationships" requires `Task` to import `TaskRelationship`. Taken literally and directly, these two instructions cannot both be satisfied by ordinary top-of-file imports - Python would raise on whichever module loads second. Resolved with a standard, narrowly-scoped technique rather than any architectural change to either package: `argus/task/task.py` imports `TaskRelationship` only under `typing.TYPE_CHECKING` (a compile-time-only guard, never evaluated when the module actually runs) and spells the field's own type annotation as a forward-reference string, `Sequence["TaskRelationship"]` - Python's dataclass machinery never needs to resolve that string at runtime, since this codebase does no reflective type-validation on its own dataclasses anywhere. The one place that genuinely needs the real class at runtime - `TaskBuilder.with_relationship()`'s own `isinstance()` check - lives in `argus/task/builder.py`, a separate module `argus.task_relationship.relationship` never imports, so no cycle actually exists once the dependency is examined at the level of which module imports which at runtime, rather than at the level of which package "depends on" which in the abstract.

## Package 034 - Capability Executor

Built the first genuine dispatch step between `ExecutionEngine` and the `Capability Registry`: `CapabilityExecutor`, a new core service that takes each `Task` an `ExecutionEngine.execute()` call is processing and asks the Capability Registry, by name, whether a matching `Capability` exists. "The Capability Executor resolves a Capability for a Task and produces an immutable CapabilityExecutionResult... It establishes the execution contract only." Nothing found is ever invoked, and nothing about `ExecutionEngine`'s own outcome for a Task changes based on what comes back - "This package introduces dispatch only - not execution policy."

The one substantive design decision this package required, beyond assembling the now-familiar value-object/status/metadata/builder quartet, was how `ExecutionEngine`'s own constructor should change. Package 033 had already given `ExecutionEngine.__init__()` a `capability_registry: ICapabilityRegistry` parameter, stored but genuinely unused - explicitly "to establish future wiring." This package's own work order supplies that future wiring, but leaves open whether `ExecutionEngine` should now hold *both* a `CapabilityExecutor` and its own direct `CapabilityRegistry` reference, or whether the new dependency should replace the old one outright. The Architectural Position diagram settled it: a single, linear chain - `Execution Engine -> Capability Executor -> Capability Registry -> Capability` - with no skip-level arrow from Execution Engine directly to the Registry. Read alongside the Bootstrap section's own "ExecutionEngine now owns: CapabilityExecutor" (not "also owns"), the `capability_registry` parameter was removed and replaced by `capability_executor: ICapabilityExecutor` - a breaking constructor change, but one with no live call site that ever needed the old parameter directly in the first place, since Package 033's own version never called it either.

A smaller, but still genuine, interpretive question concerned `CapabilityExecutionStatus`'s own five members. The work order's own Resolution behavior section reads, verbatim: "If a Capability exists whose name exactly matches the Task name, return: status = COMPLETED. Otherwise return: status = NOT_FOUND." `RESOLVED` sits right there in the enum's own member list, and reads as the more semantically apt choice for "a Capability was found" - `COMPLETED` more naturally suggests the underlying work is actually done, which this package explicitly does not do. ## Package 035 - Capability Context

Built the value object that will eventually give a Capability everything it needs to actually do its work: `CapabilityContext`, an immutable snapshot carrying the `Task` a Capability concerns, the `Plan` that Task belongs to, the `ExecutionTrace` recorded so far (when available), and descriptive metadata. "A CapabilityContext represents all information available to a capability when it eventually performs work... The context is simply created and passed through the execution pipeline." Nothing performs any work with it yet - "No execution behavior. No AI. No tool invocation. No APIs" - it is purely plumbing for a future package.

The one substantive design decision this package required was how `CapabilityExecutor.resolve()`'s own signature should change. The work order is explicit that `CapabilityExecutor now accepts CapabilityContext instead of a bare Task` - the word "instead," together with the Architectural Position diagram's own single-chain shape (`Execution Engine -> Capability Context -> Capability Executor`, no skip-level arrow bypassing the context to hand `resolve()` a bare Task directly), settles this as a genuine breaking replacement, not an additive overload. That immediately raised a smaller question: what happens to `InvalidTaskReferenceError`, which Package 034 used to validate `resolve()`'s own outer parameter directly? Discarding it felt wasteful - a `CapabilityContext` can still carry a malformed `task` field even after being validated as a `CapabilityContext` itself - and reusing it to validate the outer `context` parameter too would have made one exception mean two different things depending on which layer failed. The resolution: add a new exception, `InvalidCapabilityContextReferenceError`, for the outer check, and keep `InvalidTaskReferenceError` genuinely alive by moving what it validates one level down, to the extracted `context.task` value. Both exceptions are raised, tested, and meaningful; neither goes dormant.

A closely related naming question came up almost immediately: `CapabilityContextBuilder`'s own `with_*()` methods needed an exception for malformed field input (a non-Task passed to `with_task()`, and so on) - the same role `InvalidCapabilityExecutionResultError` (034) plays for its own sibling builder. The obvious name, `InvalidCapabilityContextError`, sits uncomfortably close to the brand-new `InvalidCapabilityContextReferenceError` just added to a *different* package (`argus.capability_executor.exceptions`) for a *different* purpose (validating `resolve()`'s outer parameter). Rather than let two exceptions with nearly identical names quietly diverge in meaning across a package boundary, both got a short "Naming Note" in their own module docstrings cross-referencing the other and explaining exactly why they are not the same thing.

The most interesting tension, though, was architectural rather than naming: `CapabilityContext.execution_trace` is a real field this package's own work order names, but `ExecutionEngine.execute(plan)`'s own signature is untouched by this package, and no genuine `ExecutionTrace` object exists at the point `execute()` runs in the first place - it gets built later, inside `AgentService.run()`, only after every trace step describing `execute()`'s own effects (including this very package's own new step) has already been recorded onto it. There is no way for `ExecutionEngine` to hand a real, finished `ExecutionTrace` to a `CapabilityContext` it constructs mid-`execute()`, because that trace doesn't exist yet. The resolution mirrors a precedent already set at the enum level - `ExecutionStatus.FAILED`/`CapabilityExecutionStatus.RESOLVED` both sit reserved, defined but never produced, until a future package gives them a genuine code path - applied here to a field instead: every `CapabilityContext` `ExecutionEngine` constructs in Version 1 simply carries `execution_trace=None`, which is not a workaround but the literal, only-available way to satisfy this package's own "every field defaults" requirement given the construction-time ordering constraint. Documented plainly, not left as a silent gap.

The Bootstrap question resolved itself almost entirely through direct inspection rather than judgment. The work order's own instruction is conditional - register `CapabilityContextBuilder` "only if the existing architecture registers builders as services; otherwise, do not register it" - and a quick grep across `bootstrap.py` for any `Builder(` construction or `container.register(...)` call naming a builder turned up nothing, for any builder, ever, across this codebase's entire history. `ContextBuilder`, `PlanningSessionBuilder`, `TraceBuilder`, `TaskBuilder`, `RelationshipBuilder`, `ExecutionResultBuilder`, and `CapabilityExecutionResultBuilder` are all constructed locally by their own callers. That settles the conditional cleanly in favor of "do not register it" - `bootstrap.py` is untouched by this package, the first package since 026 with genuinely zero `bootstrap.py` changes of any kind.

One repository-process note, continuing the streak established since Package 015: the uploaded repository ("ArgusOS (34).zip") passed pre-flight verification cleanly on every check - HEAD sits exactly one commit ahead of tag `v0.3.4`, a minimal 1-line version-only sync (`argus/bootstrap.py`, `CORE_SERVICES_VERSION` from `"0.3.3"` to `"0.3.4"`), nothing unusual, the twenty-first consecutive package (015-035) with no process anomaly of any kind.

The standalone smoke checks caught one genuine slip, worth recording precisely because it was the only implementation mistake made anywhere in this package: `ICapabilityContextBuilder`'s abstract methods were initially written with explicit `raise NotImplementedError` bodies beneath their docstrings - a style that reads naturally but, unlike every sibling builder interface in this codebase (which use docstring-only abstract method bodies with no executable statement), registers as an uncovered line in every abstract method once coverage measurement ran. Caught immediately on the first coverage pass, fixed by removing the bodies to match the established convention, restoring 100% on the very next measurement - not a design error, just a stylistic slip corrected before it could compound into a real gap.
